# WitDatabase audit — July 2026

Sixteen parallel audits, every blocker/critical/major finding then put through an adversarial
verifier whose default was to refute it. 90 findings survived verification; 4 were refuted
outright; 74 minor/nit items were never adversarially checked and are listed separately.

**Disclosure on coverage:** verification was capped at the five highest-severity findings per
dimension. **104 further blocker/critical/major findings were reported but never adversarially
verified** and are therefore not in §4. Treat §4 as a verified floor, not a ceiling.

All paths are relative to the repo root.

---

## 0. Verified by execution

Everything in this section was **run**, not inferred, on Windows 11 / .NET 9 & 10 / `dotnet ef`
10.0.8 at commit `c9d5a85`. Baseline: the solution builds clean and `dotnet test` is **green**
(~5,000 tests). Harnesses are described in §6.

### 0.1 KnownIssue #1b — root cause established

§4.1 below says #1b was not root-caused. **It now is, and it is not in the engine.**

`AddEntityFrameworkWitDb` never registers `IProviderConventionSetBuilder`
([WitDbServiceCollectionExtensions.cs:35](Sources/Providers/OutWit.Database.EntityFramework/Extensions/WitDbServiceCollectionExtensions.cs#L35)),
so the **core** builder is used instead of a relational one. Measured:

```
IProviderConventionSetBuilder = ...Conventions.Infrastructure.ProviderConventionSetBuilder
TableNameFromDbSetConvention present = False
```

Consequence: default table names come from the entity CLR type, not the `DbSet` property, so the
**same model produces different table names under WitDatabase than under every other EF provider**:

| | Npgsql | WitDatabase |
|---|---|---|
| table | `Websites` | `Website` |
| primary key | `PK_Websites` | `PK_Website` |
| index | `IX_Events_…` | `IX_Event_…` |

Confirmed against the real consumer: `OutWit.Analytics.Database.PostgreSql/Migrations/…InitialCreate.cs`
creates `Websites`/`Events`/`Sessions`; `OutWit.Analytics.Database.WitDatabase/Migrations/…InitialCreate.cs`
creates `Website`/`Event`/`Session` from that same `WitAnalyticsDbContext`.

So the hand-written `AddColumn(table: "Websites")` — copied from the PostgreSql migration — failed
with `Table 'Websites' not found` because **no such table existed**; the provider had created
`Website`. That is consistent with every fact in `KnownIssues.md`, including "every subsequent query
reads it happily" (EF queries use `Website` and work).

Proven fix — adding a concrete `RelationalConventionSetBuilder` subclass restores parity:
```
IProviderConventionSetBuilder = WitConventionSetBuilder
entity Event -> table "Events"     entity Website -> table "Websites"
```
Also absent for the same reason: `RelationalValueGenerationConvention` (identity/computed columns),
**`RelationalDbFunctionConvention` — i.e. `HasDbFunction`/UDF support cannot work at all**,
`SharedTableConvention`, `TableSharingConcurrencyTokenConvention`, `StoreGenerationConvention`,
`RelationalMaxIdentifierLengthConvention`, `EntityTypeHierarchyMappingConvention`,
`RelationalQueryFilterRewritingConvention`.

This is the single highest-leverage fix in the report: one missing registration, and it explains a
blocker, the table-name divergence, and part of the UDF gap.

### 0.2 KnownIssue #1a — reproduced end-to-end and fix validated

§4.1's mechanism is confirmed exactly. `dotnet ef migrations add InitialCreate` against a model
mirroring WitAnalytics produced singular table names, **no `maxLength:` anywhere** (the runtime model
does carry `maxLen=100/255/50/500/64`), columns in name order, and an **empty `Down()`** — the same

protected override void Down(MigrationBuilder migrationBuilder) { }

The command printed `Done.` and the snapshot **does** contain `b.Property<string>("ExcludedPaths")`.
Model and database diverge permanently, silently.

                                    in the read-optimized model...
[+ relational conventions]          stock differ THREW (same)
[+ conventions + stock initializer] stock differ OK, 4 ops

With both stock services restored, the differ output is **identical to Npgsql's** — declaration
order, `maxLength`, plural names:

CreateTable "Events":   Id, WebsiteId, UrlPath(500), VisitorHash(64), …               pk=PK_Events fks=1

[WitModelRuntimeInitializer.cs:12-15](Sources/Providers/OutWit.Database.EntityFramework/Infrastructure/WitModelRuntimeInitializer.cs#L12-L15)

### 0.4 `COUNT(*)` can disagree with the rows — and it hid two other defects

`COUNT(*)` is served from `SchemaCatalog`'s row counter, not from the data, and the two diverge.
Measured (each cell: counter vs. rows actually returned by a `SELECT`):

| Scenario | `COUNT(*)` | rows a `SELECT` returns |
|---|---|---|
| `DROP TABLE T` then `CREATE TABLE T` again | 0 | **2** — and `SELECT V WHERE Id=1` returns `'old'` |
| same, across a file reopen | 0 | **1** |
| `TRUNCATE TABLE users` after `CREATE TABLE Users` | 0 | **2** |
| unique-index violation, after reopening the file | 1 | **2** — the rejected row `Id=2, V=7` is there |
| `INSERT INTO users` + `INSERT INTO Users` (one table) | 2 | **1** — the lowercase row is unreadable |

Three consequences worth separating out:

1. **`DROP TABLE` really does orphan rows** (§4.8), and a recreated table silently serves the old
   table's data. In-session `COUNT(*)` says 0, so this is invisible to any test that counts.
2. **The unique-index defect (§3 item 15) is confirmed** — the violating row survives the exception
   and is visible after a reopen. A first pass using `COUNT(*)` wrongly cleared it.
3. **`COUNT(*)` lying is its own finding**, not present in §4: EF's `.Count()` returns 0 where
   `.ToList()` returns 2 rows. Any code that branches on `Count() == 0` is unsafe. Add it to week 1.

Not reproduced: `DROP INDEX` + recreate adopting stale entries (0 rows, correct — the
`EnsureDeleted` variant in §4.8 may still hold); `ROLLBACK` leaving the index divergent for this
shape; DECIMAL index range scan dropping rows for two-decimal money values;
`Math.Max` collapsing to the aggregate (returned 5 scalar rows correctly).

### 0.5 Space is not reclaimed

Fill 2,000 rows × ~180 B, then five rounds of `DELETE FROM T` + refill the same 2,000 rows:

```
after initial fill:            1,564 KB
after 5 delete-all + refill:  10,788 KB   (6.9x, expected ~1x)
```

Confirms §4.3's "delete never merges, rebalances or frees pages". For a long-running service this is
unbounded growth with no `VACUUM` to recover it. 60 insert+delete cycles of 40 KB overflow values did
*not* exhaust the pinned page cache, so §3 item 2's failure mode needs more pressure than that to
surface — the code defect is still real.

### 0.6 Encryption: fails closed, but the key schedule is the problem

§1 and §4.7 call at-rest encryption "cryptographically void". That overstates one half and
understates the other, so to be precise — measured:

- wrong password → `CryptographicException`. **Fails closed.**
- no password on an encrypted file → `InvalidDataException`. **Fails closed.**
- a `PLAINTEXT-CANARY` value written through an encrypted connection was **not** found in cleartext
  in any file on disk.

So the AEAD tag is checked and plaintext does not leak to the main file. What *is* broken is the key
schedule, confirmed by reading
[CryptoUtils.cs:51](Sources/Core/OutWit.Database.Core/Utils/CryptoUtils.cs#L51):
`DerivePasswordSalt(password) = SHA256(password + "_WitDB_Salt")[..16]`. The salt is a pure function
of the password, so it contributes **zero entropy**: identical passwords give identical keys in every
database ever created, which makes precomputation viable and defeats the entire purpose of a salt.
PBKDF2-SHA256 at 100,000 iterations is otherwise a reasonable choice. Combined with the nonce reuse
in §4.7, §3 item 21 stands as written — but the honest summary is "the key schedule and nonce
discipline must be rebuilt", not "encryption does nothing".

### 0.7 A blocker-class defect no dimension found: the schema catalog deserializes to *empty*

Raised by the completeness critic and confirmed by reading:
[SchemaCatalog.Persistence.cs:20](Sources/Engine/OutWit.Database/Schema/SchemaCatalog.Persistence.cs#L20)
calls `tablesData.FromMemoryPackBytes<List<DefinitionTable>>()` **with no logger**, and that helper
(`Common/Serialization/MemoryPack/OutWit.Common.MemoryPack/MemoryPackUtils.cs:76-88`) is
`catch (Exception e) { logger?.LogError(…); return default; }`.

So *any* failure to deserialize the schema blob — a torn write, a `DefinitionTable` shape change
between library versions, a format break — yields `null`, an empty catalog, and
`Table 'X' not found` **for every statement**, with zero diagnostics. The next DDL then calls
`SaveSchema()` and overwrites the blob with the near-empty list: permanent catalog loss with the row
data still on disk. `FORMAT_VERSION = 0x0100` is written at
[DatabaseHeader.cs:151](Sources/Core/OutWit.Database.Core/DatabaseHeader.cs#L151) and **never
compared on read**, and this report prescribes at least five format breaks. Make `LoadSchema` throw,
gate the format version, and version the schema blob **before** shipping any of them.

### 0.10 Schema qualification is silently dropped, then fatal

```
ALTER TABLE dbo.Websites ADD COLUMN …      -> InvalidOperationException: Table 'dbo.Websites' not found
ALTER TABLE "dbo"."Websites" ADD COLUMN …  -> InvalidOperationException: Table 'dbo.Websites' not found
```
[WitSqlVisitor.Helpers.cs:78-91](Sources/Engine/OutWit.Database.Parser/Visitor/WitSqlVisitor.Helpers.cs#L78-L91)
builds a composite `"schema.table"` key; `SchemaCatalog` has no notion of schemas. Meanwhile
`WitMigrationsSqlGenerator.cs` never emits `operation.Schema` at all — zero occurrences in the file —
so `HasDefaultSchema(...)` / `ToTable(name, schema)` is accepted by the model builder and then
ignored. Reject it in `WitModelValidator` or implement it; silent acceptance is the worst option.

## 1. Verdict

The engine is further along than its defect list suggests: the B+Tree read path, the LSM read path
(version precedence, tombstone shadowing, bloom round-trip), constraint enforcement at DML time,
set operations, window functions, CTEs, `RETURNING`, and the plugin/provider registry are all
genuinely sound — the registry in particular is reflection-free, `[ModuleInitializer]`-driven, and
ALC/AOT-safe, so the architectural bet that motivated the whole project is correct and paid off.
**It is not ready to be the file backend of the plugin architecture today**, and the reason is not
the two blockers you already know about: it is that two concurrent `DbContext`s cannot open one
`.witdb` at all ([StorageFile.cs:57](Sources/Core/OutWit.Database.Core/Storage/StorageFile.cs#L57)
uses `FileShare.None`, each `WitDbConnection` builds its own engine), which rules out any ASP.NET
Core scoped-DbContext usage — exactly the WitIdentity shape. **For test/dev use it is usable today
with caveats**: single-connection, non-parallel, file-backed, no `UseWitDbInMemory()` (that mode
cannot survive EF's per-operation connection close), and fixtures must not reset by
`EnsureDeleted()` on a fixed path (the sibling `*_indexes/` directory survives and a recreated index
silently adopts the stale entries, producing phantom UNIQUE violations on an empty table).
**For a customer with real data, no** — three independent silent-corruption paths are confirmed:
a size-blind B+Tree split that drops rows while reporting success
([BTree.Insert.cs:600](Sources/Core/OutWit.Database.Core/Tree/BTree.Insert.cs#L600)), `DROP COLUMN`
re-serializing surviving columns against the old type list
([WitSqlEngine.Ddl.Tables.cs:307](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Ddl.Tables.cs#L307)),
and a `LIKE` operator-precedence bug that turns `WHERE x NOT LIKE 'p%' AND id = 5` into a
whole-table `DELETE`
([WitSqlParser.g4:490](Sources/Engine/OutWit.Database.Parser/Grammars/WitSqlParser.g4#L490)).
At-rest encryption **does** fail closed and does not leak plaintext to disk (§0.6), but its key
schedule is broken — the salt is a pure function of the password, and the nonce counter restarts at 0
on every open and for every index file — so it must not be advertised until rebuilt.
The three things that most limit the project, in order: **(1)** single-writer file exclusivity;
**(2)** the parser's expression-precedence defects, which are cheap to fix and silently wrong until
they are; **(3)** the absence of any crash/fault-injection harness, which is why the durability
layer's inverted write orderings went unnoticed for so long.

All three KnownIssues are now root-caused, and **two of them share one cause**: the provider never
registers an `IProviderConventionSetBuilder` (§0.1), so table names diverge from every other EF
provider — that is **#1b** — and `WitModelRuntimeInitializer` hands the migrations differ a
read-optimized model whose exception is then swallowed into an empty migration — that is **#1a**
(§0.2). **#2's root cause is not in the parser's fault at all** — it is EF's stock temporal type
mappings emitting ANSI `TIMESTAMP '…'` literals the grammar has no production for, and it breaks
`DateTime` too, not just `DateOnly` (§0.9). **#3 is exactly what it looks like** and is the least
important item in this report.

**Two findings arrived after the main sweep and belong in week 1**: `COUNT(*)` is served from a
counter that demonstrably disagrees with the stored rows (§0.4), and inline `decimal` literals lose
precision silently (§0.9). Both are cheap to fix and both are the kind of defect a financial or
analytics consumer discovers in production rather than in a test.

### 4.1 EF migrations

**Design-time relational model is built over the RuntimeModel; the differ swallows the resulting exception into an empty migration — blocker.** *(= KnownIssue #1a, root cause found)*
[WitModelRuntimeInitializer.cs:91-94](Sources/Providers/OutWit.Database.EntityFramework/Infrastructure/WitModelRuntimeInitializer.cs#L91) · [WitMigrationsModelDiffer.cs:67](Sources/Providers/OutWit.Database.EntityFramework/Migrations/WitMigrationsModelDiffer.cs#L67) · [:49](Sources/Providers/OutWit.Database.EntityFramework/Migrations/WitMigrationsModelDiffer.cs#L49)

`InitializeModel` replaces EF's `RelationalModelFactory` with a closure that redirects to the
`ReadOnlyModel` runtime model and hardcodes `designTime: false`. `ModelRuntimeInitializer.Initialize`
adds `ReadOnlyModel` *after* calling `InitializeModel`, and the Wit factory is lazy, so by the time
anyone calls `GetRelationalModel()` the redirect always fires — including for
`IDesignTimeModel.Model`. `MigrationsModelDiffer` then reads `RuntimeIndex.IsDescending` (and
`ITable.CheckConstraints`), which throw `InvalidOperationException("…read-optimized model…")`. The
`catch … when (ex.Message.Contains("read-optimized model"))` returns `Array.Empty<MigrationOperation>()`
whenever `source != null`, i.e. every incremental migration. `GetDifferences` is not lazy, so
operations already computed are discarded. `HasDifferences` has the same swallow, so
`has-pending-model-changes` and the Migrator's pending-changes warning are blinded too.

Repro without `dotnet ef`: two contexts over the same table differing by one property, each with at
least one `HasIndex`; assert `differ.GetDifferences(v1Rel, v2Rel)` contains one `AddColumnOperation`
and `HasDifferences` is true. Both fail. One-liner on any existing context:
`ctx.GetService<IDesignTimeModel>().Model.GetRelationalModel().Model.GetType().Name` prints
`RuntimeModel`.

**Fix — order matters.** The auditor said "just delete the initializer". The verifier proved that
is a regression: the provider registers **no** `IProviderConventionSetBuilder`, so
`RelationalRuntimeModelConvention` is absent, and the hack is currently load-bearing for
`GetTableMappings()` on the runtime model. So:
1. Add `WitConventionSetBuilder : RelationalConventionSetBuilder` and
   `.TryAdd<IProviderConventionSetBuilder, WitConventionSetBuilder>()`.
2. Delete `WitModelRuntimeInitializer` and its registration.
3. Delete `WitMigrationsModelDiffer` and its registration (its `BuildCreateOperations` also loses
   seed data, `EnsureSchema` and topological ordering).

Expect fallout: step 1 also enables `TableNameFromDbSetConvention`, so default table names change
from entity-type name to DbSet name — a fidelity *fix*, but schema-affecting for existing `.witdb`
files. `WitMigrationsModelDifferTests.cs:78-79` asserts the old name and will need updating.
If step 1 cannot land immediately, change `:67` and `:49` to `throw;` — a loud
`migrations add` failure beats a silent one that advances the snapshot.

Note also: with no index in the model the message filter does not match and you get an uncaught
`InvalidCastException` from `AddSeedData` instead. `ForeignKeyIndexConvention` gives almost every
real model an index, so the silent path is the common one.

[WitSqlEngine.Ddl.Tables.cs:186,217](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Ddl.Tables.cs#L186) · [SchemaCatalog.Persistence.cs:63](Sources/Engine/OutWit.Database/Schema/SchemaCatalog.Persistence.cs#L63)

### 4.2 Parser

**`LIKE` pattern parsed at precedence 0 — blocker.**
[WitSqlParser.g4:490](Sources/Engine/OutWit.Database.Parser/Grammars/WitSqlParser.g4#L490)

`| expression NOT? LIKE expression (ESCAPE expression)? # likeExpr` — the trailing optional block
means ANTLR generates `expression(0)` for the pattern (and for the ESCAPE operand), so the pattern
greedily absorbs any following `AND`/`OR`/comparison. Verified by regenerating a Java parser from
these exact `.g4` files with the vendored 4.13.1 jar. `GLOB` is unaffected because its pattern *is*
the last element.

`SELECT * FROM T WHERE Name LIKE 'John%' AND Id = 1` → 0 rows (pattern evaluates to `"true"`/`"false"`
and matches nothing). `DELETE FROM T WHERE Name NOT LIKE 'John%' AND Id = 3` → **deletes the whole
table**, because `NOT LIKE` inverts the never-matching pattern. The repo's own
[ProductService.cs:179](Samples/OutWit.Database.Samples.WebApi/Services/ProductService.cs#L179)
(`WHERE LOWER(Name) LIKE @search OR LOWER(Description) LIKE @search`) can never return a row.

Fix (regenerated and verified): split into two alternatives, ESCAPE form first, so a bare recursive
reference is always last:
```
| expression NOT? LIKE expression ESCAPE expression   # likeEscapeExpr
| expression NOT? LIKE expression                     # likeExpr
```
plus a new visitor arm at
[WitSqlVisitor.Expressions.cs:109](Sources/Engine/OutWit.Database.Parser/Visitor/WitSqlVisitor.Expressions.cs#L109).
EF-generated SQL is accidentally safe (EF parenthesises `LikeExpression`); raw SQL, ADO.NET, Studio
and `FromSqlRaw` are not.

**`BETWEEN` low bound at precedence 0 — critical.**
[WitSqlParser.g4:488](Sources/Engine/OutWit.Database.Parser/Grammars/WitSqlParser.g4#L488)

Same mechanism (interior recursive reference → `expression(0)`), and both readings consume the whole
input so ANTLR resolves greedily. `WHERE Age BETWEEN 18 AND 65 AND IsActive = TRUE` parses as
`Age BETWEEN (18 AND 65) AND (IsActive = TRUE)` → degenerates to `Age >= 1 AND Age <= 0|1` → zero
rows. `OR` is unaffected (the required `AND` delimiter forces the right split).
`DELETE FROM E WHERE Age NOT BETWEEN 18 AND 65 AND IsActive = TRUE` deletes nearly everything.

Fix: split the boolean layer out of `expression` into a `valueExpression` rule (Trino/standard-SQL
shape) so bounds/patterns cannot reach `AND`/`OR` at all. That also fixes `LIKE` structurally. A
narrower AST re-association pass in the visitor works but must handle `Or` links for `LIKE`.

**Prefix `NOT` given higher precedence than every comparison — major.**
[WitSqlParser.g4:479](Sources/Engine/OutWit.Database.Parser/Grammars/WitSqlParser.g4#L479)

`(PLUS | MINUS | NOT | TILDE) expression` sits at precedence 20, above `*`, `=`, `IS NULL`, `IN`,
`LIKE`. `WHERE NOT Age > 30` → `(NOT Age) > 30` → always 0 rows. `WHERE NOT Id = 1` returns the
exact complement of the correct set. Grouping `+ - ~` high is correct; only `NOT` is misplaced.

Fix: keep `(PLUS | MINUS | TILDE) expression` where it is; add `| NOT expression # notExpr`
immediately above `andExpr`, plus a visitor arm. Not reachable from EF (the provider parenthesises
`NOT (...)` at
[WitQuerySqlGenerator.cs:65](Sources/Providers/OutWit.Database.EntityFramework/Query/WitQuerySqlGenerator.cs#L65));
reachable from all raw-SQL paths and from hand-written CHECK/trigger/index predicates.

### 4.3 Core storage — B+Tree, overflow, LSM

**Split ignores the `InsertLeaf`/`InsertInternal` return value — blocker.**
[BTree.Insert.cs:600,605](Sources/Core/OutWit.Database.Core/Tree/BTree.Insert.cs#L600) (+ `:685,690` async, `:754,760` internal, `:817,823` internal async)

`SplitLeaf` clears the node (which does *not* zero the cell directory) and replays all entries
ignoring the boolean. The split point is chosen by entry **count** (`totalCount / 2`) with no regard
to size, so a half can fail to fit. Two consequences: the entry is dropped while
`PropagateSplitUp` still increments `m_entryCount` and `Insert` returns **true**; and because
`InsertLeaf`'s shift loop is a no-op when `index > KeyCount`, a subsequent successful insert writes
a live directory slot whose offset was never set, so `GetKey` decodes the page header as a key and
the leaf's keys stop being monotonic.

Verified by simulation against the real constants (page 4096 → capacity 4064, MaxInlineValueSize
960): 5 rows with 10-byte values then 4 rows with 960-byte values fills a leaf to 4038/4064;
inserting a 5th 960-byte row splits with `splitPoint=5`, right half needs 4885 > 4064 → the new row
is silently discarded. Reachable from SQL because `StoreBTree` is the default store and
`InsertRow` honours supplied PKs (so out-of-order keys are normal for EF).

Fix: size-aware split point (prefix sums of `CalculateLeafEntrySize + CELL_DIR_ENTRY_SIZE`, pick the
candidate closest to half the bytes among those where both halves fit; 3-way split as fallback);
reject at `Insert()` any entry exceeding `PageSize - CELL_DIR_OFFSET`; throw on any replay that
returns false; bounds-check `index` in `InsertLeaf`/`InsertInternal`.

**`FreeOverflow` releases the wrong page — critical.**
[PageManagerOverflow.cs:237](Sources/Core/OutWit.Database.Core/Managers/PageManagerOverflow.cs#L237)

`currentPage` is overwritten with the *next* page number inside the `try`, and the `finally`
releases that new value. Every non-terminal link leaks a pin. The async twin at `:504` gets it
right, which confirms the intent. Pinned pages are unevictable, so a long enough chain (or ~40
multi-page frees with the default 1000/16-shard cache) hits
`InvalidOperationException("Cache is full and all pages are pinned")` from an unrelated statement,
after which that connection is permanently poisoned. On the way there, every `AllocatePage` that
tries to reuse a pinned page takes a degraded path that hands out an uncleared page.

Fix: `uint pageNum = currentPage; var cachedPage = GetPage(pageNum); try { … } finally { ReleasePage(pageNum); }`.
Add a debug `TotalPinCount == 0` assertion at `PageManager.Dispose`.

**`Delete` never merges, rebalances or frees pages — major.**
[BTree.Delete.cs:38](Sources/Core/OutWit.Database.Core/Tree/BTree.Delete.cs#L38) (`:90` async)

Delete does exactly three things: free the overflow chain, `RemoveAt`, decrement the count. No
underflow check, no merge, no leaf-chain unlink, no `FreePage`. `MergeFrom`, `MoveEntriesToRight`,
`IsUnderfull` and `MinKeys` are dead code — and `MoveEntriesToRight` writes the separator key into
the *source* node ([BTreeNode.Split.cs:72](Sources/Core/OutWit.Database.Core/Tree/BTreeNode.Split.cs#L72)),
while `MergeFrom` can bail out after already inserting entries. So `PageManager.FreePage` has
exactly one production caller (`PageManagerOverflow`) and tree pages are never reclaimed.

Retention workload (insert 200k, delete 199k): `FreePageCount` stays 0, `TotalPageCount` stays at
the high-water mark, and a full scan walks ~all the original leaves for 1000 surviving rows because
`CollectPageEntries` follows `nextLeaf` through empty pages. Note overflow chains *are* freed, so
this only affects inline values (≤ ~1 KB) — i.e. ordinary analytics rows.

Cheap partial fix (kills both symptoms in the repro): when `RemoveAt` empties a non-root leaf,
unlink it from Prev/Next, remove the parent separator, `FreePage` it. Full borrow/merge is a week
and needs the two helpers fixed first.

**Any 9-byte inline value starting with `0xFF` is misread as an overflow reference — major.**
[BTreeNode.CellAccess.cs:118-121](Sources/Core/OutWit.Database.Core/Tree/BTreeNode.CellAccess.cs#L118)

Overflow refs are recognised by shape only (`length == 9 && value[0] == 0xFF`), with no per-cell
tag. `db.Put(key, new byte[]{0xFF,0,0,0,0,1,2,3,4})` succeeds and then the entry is **unreadable and
undeletable** — `Get`, `Put`-over and `Delete` all route through `FreeOverflow`/`ReadOverflow` on a
bogus page number. Reachable in three lines from the README's headline KV API. The SQL/EF path is
immune (row payloads carry a `ushort` count prefix; index values are 8-byte rowids).

The verifier refuted the "frees live pages" consequence: B+Tree pages' bytes 2..6 are
`CellCount`/`FreeSpaceStart`, which decode to an out-of-range page number and throw first. Actual
corruption is *conditional* — only if the sniffed page number happens to land on a genuine overflow
page, in which case another key's chain is freed.

Fix (stage 1, format-compatible): force overflow whenever a value would be indistinguishable from a
ref, at all six `value.Length > m_maxInlineValueSize` sites. Stage 2: encode the flag in the
value-length varint low bit. Defence in depth: validate `PageType == Overflow` on every page of a
chain, not just the head.

**Index/PK keys over 1024 bytes throw a raw `ArgumentException` after the row is already written — major.**
[BTree.cs:35,361](Sources/Core/OutWit.Database.Core/Tree/BTree.cs#L361) · [WitSqlEngine.Dml.Operations.cs:93](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Dml.Operations.cs#L93)

`HasIndex(e => e.Url)` on an unbounded `string`: a 1100-byte value throws
`ArgumentException("Key too large")` out of the storage layer. Effective budget is 1011 bytes for a

`PutToStore` runs *before* `UpdateIndexesOnInsert`, and the catch there is
`InvalidOperationException`-only, so the row stays committed and un-indexed; and the counter

Fix: build and validate all index keys before `PutToStore`; translate to a `WitSqlException` naming
the index and column; validate at `CREATE INDEX` time for fixed-width column types.

**A partial `sst_*.sst` makes the database permanently unopenable — critical.**
[SSTableBuilder.cs:73](Sources/Core/OutWit.Database.Core/LSM/SSTableBuilder.cs#L73) · [StoreLsm.cs:607](Sources/Core/OutWit.Database.Core/Stores/StoreLsm.cs#L607)

then does `m_sstables.Add(new SSTableReader(file, …))` with no try/catch, so a footerless file throws
`InvalidDataException` out of the `StoreLsm` constructor, out of `WitDatabaseBuilder.BuildLsmStore`,
out of `DbContext` init — on every subsequent start. No repair path, no in-product way past it.
Reachable without a crash: an `ENOSPC` during a flush leaves the file behind and the exception is

*then* truncate the WAL / unlink compaction inputs. `Recover` must delete stray `.tmp`, quarantine an
unreadable `.sst` as `.corrupt` and continue — but keep throwing for
"encrypted but no encryptor" so a wrong password does not quarantine the whole database.

**LSM checkpoint truncates the WAL and compaction deletes its inputs before the output is fsync'd — critical.**
[StoreLsm.cs:582](Sources/Core/OutWit.Database.Core/Stores/StoreLsm.cs#L582) · [:520-523](Sources/Core/OutWit.Database.Core/Stores/StoreLsm.cs#L520)

`SSTableBuilder.Finish()` ends at `m_writer.Flush()` — no `flushToDisk` anywhere in `LSM/` (the WAL
and the rollback journal both do it correctly). The WAL is truncated on a WriteThrough handle
immediately afterwards, so the log reaches the device while the SSTable that replaced it does not.
Power loss loses up to a memtable (4 MB default) of acknowledged writes and, per the previous

**`LsmParallelWriter` reorders all buffered puts ahead of all buffered deletes — major.**
[LsmParallelWriter.cs:358-372](Sources/Core/OutWit.Database.Core/LSM/LsmParallelWriter.cs#L358)

`MergeBuffersBatch` partitions the drained buffer into `puts`/`deletes` and replays puts first, for
"locality" that does not exist (both loops hit the same memtable under the same lock). `StoreLsm` is
last-write-wins, so `Delete(k); Put(k, v); Flush();` yields `Get(k) == null` — durably, because the

intervening `FlushCurrentBuffer` does not save you. Every non-`None` parallel mode selects this
store for LSM, including `Latched`/`Optimistic`, which are documented as lock-based and
non-buffering.

Fix: replay `allEntries` in drain order. If batch reduction is wanted, collapse to the last op per
key with `ByteArrayComparer.Default`, preserving first-seen order.

**`LsmParallelStore.Get` bypasses the pending thread-local buffer — major.**
[LsmParallelStore.cs:83-95](Sources/Core/OutWit.Database.Core/Builder/LsmParallelStore.cs#L83)

`Scan` flushes the buffer (fire-and-forget), `Get`/`GetAsync` do not, and nothing drains a

[WitDatabaseBuilderParallelIntegrationTests.cs:210](Sources/Core/OutWit.Database.Core.Tests/Builder/WitDatabaseBuilderParallelIntegrationTests.cs#L210)
needs none while its LSM sibling at `:247` has one inserted.

`LsmParallelStore` to modes that actually asked for buffering.

**Compaction disposes `SSTableReader`s under a live lazy scan — major.**
[StoreLsm.cs:248-262](Sources/Core/OutWit.Database.Core/Stores/StoreLsm.cs#L248) · [:512-523](Sources/Core/OutWit.Database.Core/Stores/StoreLsm.cs#L512)

`Scan` captures lazy per-reader enumerables under the read lock, releases it, and returns a lazy
`MergeScan`. There is no refcount on `SSTableReader`, so `ExecuteCompaction` (a thread-pool task
scheduled by *any* flush that crosses `Level0CompactionTrigger`, default 4, `BackgroundCompaction`
default true) takes the write lock, disposes every reader and deletes the files while the enumerator
is mid-stream. Next `MoveNext` that crosses a block boundary throws `ObjectDisposedException` out of
a `SELECT`. Deterministic single-threaded repro exists (`BackgroundCompaction = false` + inline
compaction while an enumerator is open). Note `Get` is safe — it holds the read lock for the whole
lookup — so this is a `Scan`-only inconsistency.

Fix: refcount `SSTableReader` (`AddRef` under the read lock in `Scan`, `Release` in the iterator's
`finally`, `CloseCore` on last release, `DeleteOnClose` flag set by compaction instead of a direct
`File.Delete`). Also add the missing `try/finally` around `MergeScan` so abandoned enumerations
(`.First()`, `.Any()`) release their leases.

Related, minor: the immutable memtable is `Dispose()`d before being unpublished
([StoreLsm.cs:578](Sources/Core/OutWit.Database.Core/Stores/StoreLsm.cs#L578)). Reordering the two
lines does *not* fix it — a reader may already hold the reference. Just drop the `Dispose()`; the
memtable owns no unmanaged resource. Two stress tests have `catch (ObjectDisposedException) { }`
clauses that exist solely to swallow this
([StoreLsmTests.cs:389,406](Sources/Core/OutWit.Database.Core.Tests/LSM/StoreLsmTests.cs#L389)).

### 4.4 Durability and transactions

**MVCC — the ADO.NET/EF default — never fsyncs on commit and has no journal — critical.**
[MvccTransaction.cs:637](Sources/Core/OutWit.Database.Core/Transactions/MvccTransaction.cs#L637) · [WitDatabaseBuilder.cs:565-574](Sources/Core/OutWit.Database.Core/Builder/WitDatabaseBuilder.cs#L565)

`Commit()` applies versions, marks them committed, returns. No `Flush()` — compare the non-MVCC
`Transaction.Commit()` at
[Transaction.cs:394](Sources/Core/OutWit.Database.Core/Transactions/Transaction.cs#L394). The only
fsync in the whole MVCC stack is in `MvccTransactionalStore.Dispose()`. And `BuildJournal()` is
called *before* the `if (Options.EnableMvcc)` branch, so the journal is constructed, silently
discarded and never disposed — `Journal=wal;Mvcc=true` is accepted and does nothing (plus a leaked
file handle). `Mvcc` defaults to **true** in the connection string.

The verifier narrowed the scenario: EF closes the connection after each `SaveChanges`, and
`Close()` → `WitSqlEngine.Dispose()` → `Flush()`, so the plain EF flow *is* durable by accident.
The window is a connection held open — `Database.OpenConnection()`, an EF-level `BeginTransaction`
spanning several `SaveChanges`, an enumerated-but-unfinished reader, or Studio. Then everything
committed since `Open()` is lost, and because dirty pages are written back on cache eviction while
the header (holding `SchemaRootPage`) is only written by `PageManager.Flush()`, the file can be left
structurally inconsistent.

Fix: `m_store.Flush()` at the end of `Commit`/`CommitAsync` (inside the `try`, guarded on
`m_changes.Count > 0`), behind a `SynchronousCommit` option defaulting to true. Either wire the
journal into `MvccTransactionalStore` or throw when one is configured with MVCC. Note fsync alone
gives durability but not atomicity — a kill mid-`PageManager.Flush` can still tear a multi-page
commit.

**The default configuration wires no journal at all — major.**
[WitDatabaseBuilder.cs:489-527](Sources/Core/OutWit.Database.Core/Builder/WitDatabaseBuilder.cs#L489) · [WitDatabaseBuilderExtensions.cs:501](Sources/Core/OutWit.Database.Core/Builder/WitDatabaseBuilderExtensions.cs#L501)

`WithTransactions()` sets only `EnableTransactions`; `JournalProviderKey` defaults to null, so
`BuildJournal()` returns null and `TransactionalStore` skips `Recover()` entirely. Every journal call
site is `m_journal?.…`. This is the path taken by `WitDatabase.Create(path)`, `Open(path)` and every
ADO.NET connection without an explicit `Journal=`. The class comment says "Provides ACID guarantees
through journaling".

The verifier corrected the auditor's headline scenario: the journal is *logical* (LogPut/LogDelete
replayed into an open store), so it would not have protected against the header-ahead-of-data
torn-write the auditor described. That is a **separate** defect in
[PageManager.cs:657-676](Sources/Core/OutWit.Database.Core/Managers/PageManager.cs#L657), which
writes the header *first* then the dirty pages with one trailing fsync. Both need fixing:
default `JournalProviderKey` to `"wal"` inside `BuildJournal()` when transactions are on and storage
is file-backed; and reorder `Flush()` to pages → fsync → header → fsync.

**Encrypted LSM WAL: the entry counter is only persisted on Sync/Dispose — critical.**
[WriteAheadLogBase.cs:169,177](Sources/Core/OutWit.Database.Core/Wal/WriteAheadLogBase.cs#L169) · [LSM/WriteAheadLog.cs:89-95](Sources/Core/OutWit.Database.Core/LSM/WriteAheadLog.cs#L89)

The AEAD block id on the **write** side is the in-memory `m_entryCounter`; on the **read** side it is
the positional index. `LsmOptions.SyncWrites` defaults false, so the on-disk header says
`EntryCount = 0` for a whole session. After a kill, `Recover` replays fine, then the next append
re-uses block id 0 at file position N. On the next open, replay hits that entry with expected block
id N, `EncryptorBlock.Decrypt` returns null on the prefix mismatch, `ReadEntry` cannot distinguish
"decrypt failed" from "not encrypted", falls into the plaintext branch, fails, and `break`s —
**every entry from that point on is silently discarded, permanently**, until a memtable flush
truncates the log. Plus nonce reuse under a fixed key.

Deterministic repro exists (reset the header counter to simulate the kill). Fix: have `Replay` set
the counter to the positional index it reached, refuse to append to a reopened non-empty encrypted
WAL before replay, and make `ReadEntryData` throw `CryptographicException` on decrypt failure
instead of returning null.

**A failed or cancelled `Commit` leaves the transaction half-applied, and `Rollback` then deletes the undo journal without applying it — major.**
[Transaction.cs:376-435](Sources/Core/OutWit.Database.Core/Transactions/Transaction.cs#L376) · [RollbackJournal.cs:117-134](Sources/Core/OutWit.Database.Core/Transactions/RollbackJournal.cs#L117)

The apply loop has no catch: a throw at key N leaves keys 0..N-1 written and `State == Active`, so
`Dispose` calls `Rollback`, which clears the in-memory buffer (discarding the `OldValue`s it
already holds) and `File.Delete`s the durably-written undo journal. Note also `CommitAsync` has
`ThrowIfCancellationRequested()` *inside* the loop — a commit must not be abandonable mid-apply.

Verifier corrections: the default ADO/EF path is MVCC, whose `RollbackTransaction` does a real undo,
so this bites `Mvcc=false` and direct Core users; and the auditor's cancellation repro is racy, not
deterministic (`PutAsync` is synchronous; only a cold-cache I/O suspension creates the window).

Fix: record applied keys, undo in reverse from `m_changes[key].OldValue` on any exception, set
`State = Failed`, and delete the journal only after the undo is durable. Move the cancellation check
out of the loop.

### 4.5 MVCC

**Commit mutates already-committed versions before the new ones become visible; rollback cannot undo it — critical.**
[MvccKeyValueStore.cs:715,443](Sources/Core/OutWit.Database.Core/Stores/MvccKeyValueStore.cs#L715)

`MarkPreviousVersionDeleted` deliberately does *not* skip committed records (`record.TransactionId !=
transactionId && !record.IsCommitted` → false for a committed row), so it stamps `DeleteTimestamp`
onto a record owned by nobody. `RollbackTransaction` only removes records whose `TransactionId`
matches, so the tombstone survives while the replacement version is discarded → **the committed row
is gone, permanently**. `WithDeleteTimestamp` preserves `TransactionId`, so there is no ownership
information to undo with. Three-line repro on `MvccTransactionalStore` with no threads.

Two further consequences of the same design: **(a)** between `PutVersion` and `CommitTransaction`
(a window as wide as a full-store scan) the row reads back as **null** to every concurrent reader
including non-transactional `Get` — a row that exists momentarily does not; **(b)** an in-transaction
`DELETE` writes no record of its own, so a failure anywhere after it (including inside
`CommitTransaction`) applies the delete with nothing to roll back.

Fix: add `DeleteTransactionId` to `MvccRecord` (header 32 → 40, accept 32-byte legacy), stamp it,
make visibility ignore a pending foreign tombstone, finalize it in `CommitTransaction`, revert it in
`RollbackTransaction`, and teach `GarbageCollect` about it. Cleaner long-term: never mutate a
committed version — write a tombstone *version* owned by the writer.

**Versioned keys are prefix-ambiguous — critical.**
[MvccKeyValueStore.cs:778-799](Sources/Core/OutWit.Database.Core/Stores/MvccKeyValueStore.cs#L778)

A version lives at `key ++ BE(long.MaxValue - ts)` and is found by scanning `[key++00×8,
key++FF×8)`. For any A that is a byte-prefix of B, B's versions are inside A's range, and because
real inverted timestamps start with `0x7F` while B's next byte is ASCII (`< 0x7F`), **B's versions
sort first**. In the SQL layer `$schema:_rowid:{table}` and `$schema:_rowcount:{table}` have no
terminator, so `Event`/`EventLog` (or `Users`/`UsersCopy`) corrupt each other. On reopen — or on any
`ROLLBACK`, which calls `ReloadMetadataFromStore` — `Event`'s rowid counter reads `EventLog`'s value,
and the next INSERT overwrites a live row with no error (unique/PK validation is skipped for
auto-generated PK columns). The verifier found the write side too: `Put(A)` runs
`MarkPreviousVersionDeleted` over the same ambiguous range and can tombstone B's only live version,
making B read as null.

Fix, in order: (1) exact `IsVersionOf` filter in all four consumers — `GetRecordAsOf`,
`GetVersionCount`, `GetAllVersions` and **`MarkPreviousVersionDeleted`**; (2) fix `ScanAsOf`'s two
bound bugs; (3) longer term, order-preserving escaping of the user key before the timestamp
(format break); (4) cheap defence in depth — terminate the metadata keys with `:` and clamp the
loaded rowid to the actual max in `LoadSchema`. Note `$schema:seq:{name}` is *not* affected (its
`:val`/`:def` suffix terminates the name).

**Write-conflict detection ignores deletes — major.**
[MvccTransactionalStore.cs:530](Sources/Core/OutWit.Database.Core/Transactions/MvccTransactionalStore.cs#L530)

`HasConflict` looks only at `CreateTimestamp`. A committed DELETE creates no new version and leaves
`CreateTimestamp`/`TransactionId` untouched, so it is invisible to validation for both write set and
read set. Deterministic single-threaded repro: tx1 deletes K and commits, tx2 (older snapshot) puts K
and commits successfully → the row is resurrected. SQL Server SNAPSHOT raises 3960; PostgreSql raises
"could not serialize access due to concurrent delete". DELETE-vs-DELETE also both succeed. The
mirror case (update then delete) *is* caught, which is why nobody noticed.

Reachable only through the Core MVCC API — `WitSqlEngine` allows one active transaction and each
`WitDbConnection` builds its own store, so two MVCC transactions never share a store instance via EF.
Same fix as the tombstone-ownership change above.

**Validate-then-install is not atomic and nothing serialises commit — major.**
[MvccTransaction.cs:637-674](Sources/Core/OutWit.Database.Core/Transactions/MvccTransaction.cs#L637)

`ValidateNoConflicts` → `GetNextTimestamp` → apply loop → `CommitTransaction` with no lock held
anywhere; `BeginTransaction` explicitly takes none. Worse, `HasConflict` ignores an uncommitted
version from another transaction unless that transaction is *already* marked committed, and
`MarkCommitted` happens after a full-store scan — so the window is O(store size), not a few
instructions. Two concurrent commits on one key both pass, one update is silently lost, and the
version chain can end up with two live committed versions (after which a later DELETE tombstones only
the newest and the row reappears with a stale value — deterministic repro via the public
`IMvccStore` API).

Fix: a commit gate (`SemaphoreSlim(1,1)`) around validate → allocate → install → mark, skipped for
read-only transactions; treat an in-flight foreign writer as a conflict; per-key locking inside
`MvccKeyValueStore` for the `MarkPreviousVersionDeleted` + `Put` read-modify-write. Same
Core-API-only reachability caveat as above.

### 4.6 Concurrency

**Both page caches guard the same state with a sync `Lock` and an async `SemaphoreSlim` — major.**
[PageCacheShardedClock.cs:36-37](Sources/Core/OutWit.Database.Core/Cache/PageCacheShardedClock.cs#L36) · [PageCacheLru.cs:34-36](Sources/Core/OutWit.Database.Core/Cache/PageCacheLru.cs#L34)

The two locks do not exclude each other, yet both domains mutate `m_pages`, `m_pageIndex`,
`m_count`, `m_clockHand`, `m_firstFreeSlot`. Reachable in an **all-async** program: `LoadPageAsync`
writes `m_pageIndex` after an `await` (arbitrary pool thread) while another reader calls the sync
`ReleasePage` → `lock (m_lock)` → `m_pageIndex.TryGetValue`, reached from `BTree.Search.cs:69/80` and
`PageManager.cs:327/536`. Outcome: two callers claim the same slot (an orphaned dirty page is never
flushed and `GetPage(other)` returns the wrong page's bytes), or a false miss creates two
`CachedPage` objects for one page number. `PageCacheLru` is worse — the cache-*hit* path reorders the
linked list.

Not reachable from EF/SQL (that stack is synchronous to the cache) and not reachable in WASM
(single-threaded), so the exposure is a multi-threaded Core-API consumer — including two concurrent
`GetAsync` calls through `BTreeConcurrentStore`, which is sold as concurrency-safe. Fix by fixing
this before the async path is wired into the engine.

Fix: one `Lock` for the state, and split "reserve slot" from "do I/O" (publish a placeholder pinned
`CachedPage` + a `TaskCompletionSource`, do the read outside the lock, re-enter to complete) so no
lock is held across I/O and no slot is ever observably null while claimed. Also fix `Dispose`, which
disposes the semaphore from inside the gate.

**`BTreeConcurrentStore` holds `ReaderWriterLockSlim` across `await` — major.**
[BTreeConcurrentStore.cs:112](Sources/Core/OutWit.Database.Core/Tree/BTreeConcurrentStore.cs#L112) (+ `:150,188,274`)

RWLS is thread-affine. `LoadPageAsync` does an unconditional `await Task.Yield()` and
`StorageFile` uses `RandomAccess.ReadAsync` on a handle without `FileOptions.Asynchronous`, so the
continuation lands on a pool thread, `ExitReadLock` throws `SynchronizationLockException`, and the
lock is **leaked** — every subsequent `Put`/`Delete`/`Flush` blocks forever (no timeout is ever used;
`ParallelModeOptions.LatchTimeout` is silently dropped by the builder). One async read on a
pre-existing file with a cold cache wedges the store for the process lifetime. `Dispose()` then
throws too.

Note the auditor's `ConfigureAwait` reasoning is inverted — missing `ConfigureAwait(false)` under a
UI SyncContext is the one case that *works*. Exposure is Core-API async consumers with
`ParallelMode != None`; the EF/ADO path is synchronous throughout.

Fix: `SemaphoreSlim` (or a real async RW lock); `ConfigureAwait(false)`; honour `LatchTimeout`; add
async stress tests over a pre-existing file with `cacheSize` far below the page count.

**`AllocatePageAsync` pops the free-list head across two lock scopes — major.**
[PageManager.cs:289-336](Sources/Core/OutWit.Database.Core/Managers/PageManager.cs#L289)

The head is read under the lock, the lock is released, `GetPageAsync` is awaited, and only then is
`FirstFreePage` advanced. Nothing marks the head as claimed. The sync path does the whole pop in one
critical section, and `FreePageAsync` re-reads the header inside the second lock — so the pattern is
right twice and wrong here. Two concurrent allocators can return the same page; the tight
interleaving instead throws `"Cannot evict pinned page N"` / `"Page N already exists in cache"`
mid-insert (the async path has none of the sync path's try/catch fallback). A nastier variant: if the
page has already been re-initialised, `freeHeader.RightChild` reads 0 == `NULL_PAGE_NUMBER` and the
**entire remaining free list is dropped**. Missed by the auditor: the extend branch bumps
`TotalPageCount` under the lock but calls `SetSizeAsync` (which *truncates*) outside it.

Reachable from two `StoreBTree` instances over one shared `PageManager`, and in WASM with no threads
at all (interop awaits yield). Fix: one async gate around the whole allocation; validate the reused
page still has `PageType.Free`; make `SetSize` grow-only.

**`PageManager.FlushAsync` mutates and hands out the shared header buffer outside `m_lock` — minor.**
[PageManager.cs:694-702,865-871](Sources/Core/OutWit.Database.Core/Managers/PageManager.cs#L694)

`SaveHeaderImmediateAsync` clears the single shared `m_headerBuffer`, serializes into it and hands it
to an in-flight `RandomAccess.WriteAsync`, all outside the mutex every other header access uses. A
concurrent sync `Flush()` clears the same buffer mid-write → page 0 written as zeros → next open
either throws `InvalidDataException` or, if fully zeroed, takes the `allZeros` branch and **silently
re-initialises the file as an empty database**. Downgraded to minor because nothing in the
SQL/ADO/EF stack calls `FlushAsync`, and the async API exists for single-threaded WASM. Fix:
serialize into a rented local buffer inside the lock, write it outside; guard header write ordering
with a `SemaphoreSlim`.

### 4.7 Encryption

**Nonce reuse across sessions and across index files — critical.**
[EncryptorPage.cs:35,124](Sources/Core/OutWit.Database.Core/Encryption/EncryptorPage.cs#L35) · [EncryptorBlock.cs:33,109](Sources/Core/OutWit.Database.Core/Encryption/EncryptorBlock.cs#L33)

Nonce = `(salt[0..8] XOR pageNumber) || (int)m_writeCounter`. The counter is an instance field
initialised to 0, never persisted; the prefix is fully deterministic; and the key/salt are
deterministic functions of the password. So the Nth encryption of page P in any session equals the
Nth encryption of page P in any other session. Worse and needing no reopen:
`EncryptorProviderAesGcm.Clone()` copies the same key, and the builder creates a separate
`EncryptorPage` per secondary index with the same key and salt and its own counter at 0 — so main-DB
page 0 and each `.idx` page 0 get a byte-identical (key, nonce) pair over different plaintexts, in
one process, both on disk. For AES-GCM that is a total break: ciphertext XOR leaks plaintext XOR, and
two messages under one nonce give up the GHASH subkey H, enabling forgery of authenticated pages.
`(int)counter` also truncates a `long`. No AAD is passed at all.

**Deterministic salt — critical.**
[CryptoUtils.cs:51](Sources/Core/OutWit.Database.Core/Utils/CryptoUtils.cs#L51)
`DerivePasswordSalt(pw) = SHA256(pw + "_WitDB_Salt")[..16]`. `RandomNumberGenerator` appears nowhere
in production sources. Because the salt is also the nonce prefix, **the first 8 bytes of any
encrypted `.witdb` are `SHA256(password + "_WitDB_Salt")[0..8]` in the clear** (page 0, XOR with
zero) — an offline password verifier costing **one SHA-256 per guess**, bypassing PBKDF2's 100k
iterations entirely. `WithUserEncryption` is the *less* broken variant (username-derived salt).

Fix (format break, do it now): random 12-byte nonce per encryption; move the page/block number into
AAD (widen `ICryptoProvider.Encrypt/Decrypt`) and delete the prefix comparison — the tag is
strictly stronger; random per-file salt in an unencrypted crypto superblock at offset 0 (it cannot
live in `DatabaseHeader`, which is itself encrypted); per-file subkey via HKDF so two files with the
same password do not share a key; PBKDF2 ≥ 600k or Argon2id, with the parameters persisted; a key
verifier so a wrong password says so.

**`WithStorage()`/`WithIndexedDbStorage()` silently discard encryption — critical.**
[WitDatabaseBuilder.cs:431](Sources/Core/OutWit.Database.Core/Builder/WitDatabaseBuilder.cs#L431)
`BuildStorage` returns `Options.CustomStorage` on its first line, before the `StorageEncrypted` wrap.
The crypto provider is built and thrown away; pages are written in cleartext; and
`BuildProviderMetadata()` still sets `ProviderFeatures.Encryption` so the header *claims* encryption.
`ValidateCustomStoreCompatibility` has exactly this guard — but only for `CustomStore`, not
`CustomStorage`. This is the whole Blazor WASM path, and it is the documented example at
[Core.IndexedDb/README.md:81](Sources/Core/OutWit.Database.Core.IndexedDb/README.md#L81); the
existing test `WithEncryptionAfterIndexedDbStorageWorksTest` asserts only that the provider was
recorded. Fix: throw (short term); to actually support it, `CustomStorage` must become a deferred
factory so the inner page size can be `PageSize + Overhead`.

**Rollback journal and WAL are written in cleartext for encrypted databases — major.**
[WitDatabaseBuilder.cs:489-527](Sources/Core/OutWit.Database.Core/Builder/WitDatabaseBuilder.cs#L489)
`BuildJournal()` never looks at the crypto provider; the registered factories default `encryptor:
null`. The support is fully implemented and unreachable. `RollbackJournal` leaks the previous row
image (keys + full old rows) and the WAL leaks the new one. Fix: pass an `EncryptorBlock` with a
distinct HKDF-derived salt through `ProviderParameters`, refuse to build encrypted + unencryptable
journal, and handle the legacy-magic case at recovery (a plaintext journal is currently *silently
ignored*, so the fix would otherwise lose crash recovery for existing databases).

**`ConfigurationValidator` is never invoked — major.**
[ConfigurationValidator.cs:67](Sources/Core/OutWit.Database.Core/Providers/ConfigurationValidator.cs#L67)
The class exists to catch reopening with mismatched settings; its only caller is
`StorageDetector.GetOpeningHints`, a diagnostic API. `Validate` also does not inspect `HasMvcc` at
all, so wiring it in as-is would fix nothing. Reopening an MVCC database without MVCC reads the
versioned key space with bare keys → the schema catalog loads empty → either
`Table 'X' not found` or, with `EnsureCreated`, EF recreates every table over the old data.
`WitDatabase.Open(path)` *does* honour the persisted flags; `Open(path, password)` hard-codes
`WithTransactions()` regardless — that one needs no user error to trigger.

### 4.8 Engine — DDL and DML

**`DROP TABLE` deletes neither rows nor secondary indexes — critical.**
[WitSqlEngine.Ddl.Tables.cs:90](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Ddl.Tables.cs#L90)

Drops the implicit `_PK_` index, calls `m_schema.DropTable`, done. No `t:<table>:*` purge (compare
`TruncateTable`, which does exactly that), no `DropIndex` for user indexes. Drop+recreate the same
name and `SELECT *` returns the old rows while `SELECT COUNT(*)` returns 0 (cached counter reset); a
changed column layout decodes garbage; `CREATE INDEX` with a previously used name throws
`ArgumentException: Index 'x' already exists`; and on a file DB a re-created implicit PK index
adopts the stale `.idx` and raises spurious UNIQUE violations on an empty table. EF's usual reset
(`EnsureDeleted` → delete the file) hides it, which is why the tests are green.

Fix: enumerate `GetTableIndexes` **before** `m_schema.DropTable` (which wipes them), `Clear()` +
`DropIndex` each, purge the row range, then drop the catalog entry.

**`DROP COLUMN` corrupts the values of all columns after the dropped one — critical.**
[WitSqlEngine.Ddl.Tables.cs:307,932](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Ddl.Tables.cs#L307)
`MigrateExistingRows` deserializes *and re-serializes* with the pre-drop definition, while
`SerializeValuesArray` picks the writer by position. After the shift, position `i` holds old column
`i+1`'s value written with old column `i`'s type, and `WitTypeConverter.WriteValue` coerces silently.
`(Id INT, Name VARCHAR, Age INT)` → `DROP COLUMN Name` → `Age` reads back as **2** (the int32 length
prefix of `"42"`). Only bites when the dropped column is not last *and* a following slot's storage
type differs — which is why the EF migration test (dropping the trailing column) passes. Fix: update
the schema first and serialize with the target definition; make
`SerializeValuesArray` throw on a count mismatch instead of falling back to `StringVariable`.
`DropColumn` also performs no index maintenance.

**Case-differing table name writes into a separate key space — critical.**
[SchemaCatalog.cs:361](Sources/Engine/OutWit.Database/Schema/SchemaCatalog.cs#L361) · [WitSqlEngine.Dml.Operations.cs:90](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Dml.Operations.cs#L90)
Catalog lookup is `OrdinalIgnoreCase`; the key prefix is raw bytes. `INSERT INTO users` after
`CREATE TABLE Users` writes rows no query can see while the (case-insensitive) row-count metadata is
incremented. `DELETE FROM users` reports rows deleted and deletes nothing. `UPDATE users` creates a
phantom duplicate row *and* adds index entries without removing the old ones. `TRUNCATE TABLE users`
deletes nothing, clears the secondary indexes, and resets the rowid counter to 0 — so the next
inserts overwrite live rows one by one. `CREATE INDEX ix ON users(...)` on an existing `Users` table
builds the index from an empty scan, and once the row count crosses `MIN_ROWS_FOR_INDEX` the planner
picks that empty index and returns 0 rows with no casing mismatch at query time. `GetNextRowId`
persists `$schema:_rowid:users` while `LoadSchema` reads `$schema:_rowid:Users`, so the damage
survives a restart. Not reachable from EF (identifiers come from the model); reachable from raw SQL,
`FromSqlRaw`, seed scripts and Studio. Fix: rebind `tableName = table.Name` immediately after every
`GetTable`, and change the key helpers to take `DefinitionTable` so the compiler finds the rest.

**Row is persisted before the unique secondary index is checked, and statement validation never checks unique indexes — blocker.**
[StatementExecutor.Validation.cs:417](Sources/Engine/OutWit.Database/Statements/StatementExecutor.Validation.cs#L417) · [WitSqlEngine.Dml.Operations.cs:93,145](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Dml.Operations.cs#L93)
The pre-write validators build their constraint sets only from `col.IsUnique`, `table.PrimaryKey` and
`table.UniqueConstraints`; `CREATE UNIQUE INDEX` adds nothing to the table definition, so its
uniqueness is enforced *only* by `SecondaryIndexKeyValueStore.Add` throwing — after `PutToStore`. On
UPDATE the catch re-adds the *old* index key while leaving the *new* row value written, so the table
has two rows with the same email while the index says otherwise: an index seek returns 1 row, a table
scan returns 2, and a seek on the old value returns 0. Autocommit means it is durable; and index
mutations bypass `m_currentTransaction`, so wrapping in a transaction is not a workaround.
`HasIndex(...).IsUnique()` is exactly how EF declares uniqueness. Also: a failed INSERT skips
`IncrementRowCount`, so `SELECT COUNT(*)` (served from the counter) disagrees with a scan — a
three-way divergence. Fix: reuse `BuildIndexKey` + a probe in the pre-write validators (honouring
partial-index predicates and expression columns), and compensate on failure in
`InsertRow`/`UpdateRow` and inside `UpdateIndexesOn*` (unwind *all* index mutations, not just the
current index's).

**Secondary index writes bypass the transaction entirely — critical.**
[WitSqlEngine.Dml.IndexUpdates.cs:46](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Dml.IndexUpdates.cs#L46) · [WitSqlEngine.Transactions.cs:83](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Transactions.cs#L83)
Row writes go through `m_currentTransaction`; index writes go straight to a separate store
(`<db>_indexes/<name>.idx`) with no journal. `Rollback` restores no index state. The dangerous
direction is *missing* entries: a rolled-back DELETE (or a rolled-back UPDATE of an indexed column)
removes the index entry irreversibly while the row survives, so every index-driven plan silently
omits it — permanently, across restarts, with no `REINDEX` to repair it. The phantom-entry direction
is mostly harmless (the residual `IteratorFilter` catches it) except for the `MIN`/`MAX` index
shortcut, which returns a value straight off `GetFirstEntry`/`GetLastEntry` with no verification.
The test named `RollbackRevertsIndexChangesTest` asserts only the data side and its own comment admits
the gap; it is not in KnownIssues. Fix: per-transaction inverse-op log replayed in reverse on
rollback (and on `RollbackToSavepoint`), falling back to drop+rebuild if an inverse fails; make the
`MIN`/`MAX` shortcut re-verify the fetched row.

**Named constraints from `ALTER TABLE ADD CONSTRAINT` are never validated on UPDATE — major.**
[StatementExecutor.Update.cs:631,657](Sources/Engine/OutWit.Database/Statements/StatementExecutor.Update.cs#L657)
`AddConstraint` stores only into `table.NamedConstraints`; `ValidateConstraintsFastPath` and the
streaming path never call `ValidateNamedConstraints`. The streaming path is the catch-all (any UPDATE
with no FROM/RETURNING/BEFORE-trigger/UNIQUE-on-SET-column), so **named CHECK and FK constraints are
unenforced on practically every UPDATE**, not just PK-keyed ones. INSERT enforces them, so the
asymmetry is visible: `INSERT (-1)` rejected, `UPDATE SET = -1` accepted. Named UNIQUE *is* caught
incidentally by the implicit `UQ_` index. This is the form EF emits for `HasCheckConstraint` in a
follow-up migration. Fix: call `ValidateNamedConstraints` from both paths.

**Column-level CHECK skipped on UPDATE when the checked column is not in the SET list — major.**
[StatementExecutor.Update.cs:696](Sources/Engine/OutWit.Database/Statements/StatementExecutor.Update.cs#L696)
`if (!modifiedColumns.Contains(col.Name)) continue;` — but a column CHECK is arbitrary SQL evaluated
against the whole row, so `Hi INT CHECK (Hi > Lo)` is skipped by `UPDATE t SET Lo = 100`. The standard
path (`ValidateCheckConstraints`) has no such filter, so the two disagree. Fix: drop the filter (a
CHECK may reference any column); if cost matters, precompute referenced columns at DDL time. Note
`modifiedColumns.Count == 0` also early-returns before ROWVERSION/STORED-computed recomputation.

**DDL inside an open transaction — major.**
[SchemaCatalog.Persistence.cs:59](Sources/Engine/OutWit.Database/Schema/SchemaCatalog.Persistence.cs#L59) · [WitSqlEngine.Transactions.cs:83](Sources/Engine/OutWit.Database/Engine/WitSqlEngine.Transactions.cs#L83)
`SchemaCatalog` is constructed with `database.Store` — the `TransactionalStore` itself — so every
schema write is an auto-commit `Put`. Non-MVCC (Core default, file locking on): the transaction holds
the write lock for its lifetime and `DatabaseLock` rejects same-thread re-entry, so
`BEGIN; CREATE TABLE t(...)` throws `LockRecursionException` — from `SaveTableRowCount`, before
`SaveSchema`. On the async ADO path the thread hop turns that into a 30-second `TimeoutException`.
MVCC (ADO/EF default): no crash, but DDL is not rolled back — `BEGIN; DROP TABLE Orders; ROLLBACK;`
loses the table permanently while orphaning its rows, and `BEGIN; CREATE TABLE Tmp; ROLLBACK;`
leaves `Tmp` behind so a replayed migration dies on "already exists". Note the author already knows
the hazard: `SaveTableRowId`/`SaveTableRowCount`/`SaveRowVersion` have explicit
`if (transaction == null)` guards with a comment about lock recursion — the schema-blob writers were
never given one. Fix: thread `ITransaction?` into `SaveSchema`/`SaveViews`/`SaveTriggers`/sequence
writers, and add a `ReloadFromStore()` (full, not just row metadata) invoked from `Rollback`.

### 4.9 Engine — query and expressions

**No three-valued logic: `NULL < x` and `NULL <> x` are TRUE — critical.**
[WitSqlValue.Comparison.cs:47](Sources/Engine/OutWit.Database/Values/WitSqlValue.Comparison.cs#L47) · [ExpressionEvaluator.Core.cs:171-183](Sources/Engine/OutWit.Database/Expressions/ExpressionEvaluator.Core.cs#L171)
`CompareTo` sorts NULL first (correct for ORDER BY) and the comparison operators are defined straight
on top of it, with no NULL guard in `EvaluateBinary`. So `WHERE Age < 18` returns rows whose `Age` is
NULL. The engine is internally inconsistent: `EvaluateBetween`, `EvaluateIn` and
`CompareValues` (quantified comparisons) all have the guard. EF adds no null guard around
`<`/`<=`/`>`/`>=`, so `context.Users.Where(u => u.Age < 18)` materialises null-age entities. Also
affects DELETE/UPDATE row sets (`DELETE … WHERE col <> x` over-deletes). Index-driven plans are
accidentally correct (NULL keys are not indexed), so the answer changes with the plan.
Fix: NULL guard for the six comparison operators in `EvaluateBinary` **and** in
`EvaluateAggregateBinary` (HAVING); do not touch `CompareTo` or `GetHashCode` (hash join and group
by cache `GetHashCode` as the bucket key).

**DECIMAL index keys encoded as decimal strings — critical.**
[WitTypeConverter.cs:741](Sources/Engine/OutWit.Database/Types/WitTypeConverter.cs#L741)
`SerializeValueForIndex` writes `value.AsDecimal().ToString(InvariantCulture)` as raw UTF-8, scanned
in byte order. `"10.00" < "9"`. Two silent wrong results: (a) `SELECT MAX(Amount)` on an indexed
DECIMAL goes through the `MIN`/`MAX` index shortcut with **no residual filter and no row threshold**
and returns the lexicographic max (20 rows of 1..20 → 9); (b) `WHERE Amount >= 9` with ≥10 rows takes
a range scan and returns 1 row instead of 12 — dropping the index makes it correct. Secondary,
mixed-path: keys are scale-sensitive, so a row inserted with `10.00m` via a parameter cannot be found
by a `= 10` probe. GUID keys have the same class of problem (`Guid.ToByteArray()` is not sort-order).
Fix: fixed-width digit encoding (sign byte + 29 padded integer digits + 28 padded fraction digits,
nine's-complement for negatives) — trailing-zero-insensitive, so it fixes the scale problem too;
update `QueryPlanner.DeserializeIndexKey` in the same commit; bump the index format version. Interim:
refuse RangeScan and the MIN/MAX shortcut for Decimal/Guid/Blob key columns.

**`LIMIT -1` returns zero rows — critical.**
[WitQuerySqlGenerator.cs:99](Sources/Providers/OutWit.Database.EntityFramework/Query/WitQuerySqlGenerator.cs#L99) · [IteratorLimit.cs:59](Sources/Engine/OutWit.Database/Iterators/IteratorLimit.cs#L59)
The generator emits SQLite's `LIMIT -1 OFFSET n` for offset-without-limit (the grammar has no bare
`OFFSET`); the engine implements no such convention, and `if (m_returned >= m_limit) return false`
fires immediately at `0 >= -1`. `.Skip(n)` without `.Take()` returns an empty list — and so do
`.Skip(n).Count()` and `.Skip(n).Any()`. `-1` parses cleanly via `unaryExpr`, so the failure is
silent. `QueryWithSkipCreatesQueryableTest` asserts only that the `IQueryable` is non-null and never
enumerates. Fix: treat `limit < 0` as unbounded in `IteratorLimit` **and** `ApplyLimitClause` (which
also silently drops the offset when the limit is null) **and** the batch fast path
(`rows.Take(-1)` is also empty). Do not "fix" it by emitting `LIMIT long.MaxValue` — `(int)long.MaxValue`
is `-1` on the fast path. Optionally add a bare `OFFSET` alternative to the grammar and emit that.

**Hash join maps ON operands to inputs positionally — critical.**
[OptimizerJoinCondition.cs:131-163](Sources/Engine/OutWit.Database/Optimizers/OptimizerJoinCondition.cs#L131)
`TryExtractEquiJoinKey` checks only that the two qualifiers differ, never which input each names, and
`ComputeHashKey` then evaluates `LeftKey` against left rows. Because
`IteratorTableScan`/`IteratorAlias` never override `EstimatedRowCount` (stays −1),
`ShouldUseHashJoin` computes `(−1)*(−1)=1 > (−2)*32=−64` → hash join for **every** two-table
equi-join regardless of size. `ON o.UserId = u.Id` (joined table first) → `KeyNotFoundException` at
`Open()`. The silent case is a self-join: `Employees e LEFT JOIN Employees m ON m.Id = e.ManagerId`
resolves both operands via the bare-column-name fallback and computes
`m.ManagerId = e.Id` — the join direction is inverted, wrong rows, no error. Every ON clause in the
hash-join test file is written left-table-first. EF emits the outer key first, so the exposure is
hand-written SQL, views, `FromSqlRaw`, ADO.NET and Studio.
Fix: pass the two iterator schemas into `Analyze` and attribute each operand by `TableName`, swapping
when reversed and demoting to residual when unattributable (the residual is evaluated on the combined
row, so that is always safe). Separately, stop doing arithmetic on the −1 sentinel.

**ORDER BY / LIMIT after a set operation are applied to the left branch only — major.**
[QueryPlanner.cs:97-101](Sources/Engine/OutWit.Database/Query/QueryPlanner.cs#L97) · [QueryPlanner.Clauses.cs:341](Sources/Engine/OutWit.Database/Query/QueryPlanner.Clauses.cs#L341)
The parser attaches the trailing ORDER BY/LIMIT to the *first* SELECT and `Plan` applies them before
`ApplySetOperations`. `SELECT Id FROM A UNION ALL SELECT Id FROM B ORDER BY Id` returns the left side
sorted then the right side raw; `… LIMIT 1` returns 1 row from A plus **all** of B. UNION's dedup is
still correct (global HashSet). This is the spec's own example
([WitSQL.md:877](Docs/WitSQL.md#L877)). Not reachable from EF (its stock pushdown wraps the set op in
a derived table, which is handled correctly), so the exposure is raw SQL/Studio/ADO.
`CteWithUnionOnMainQueryTest` passes because UNION ALL preserves the row *count* — false confidence.
Fix: skip ORDER BY/LIMIT inside `Plan*Query` when `SetOperations` is non-empty and apply them to the
set-op root instead; ORDER BY then resolves against post-projection names, which is what SQL requires
for set operations anyway.

**Integer division returns a real when not exact — major.**
[WitSqlValue.Operations.cs:69-79](Sources/Engine/OutWit.Database/Values/WitSqlValue.Operations.cs#L69)
`7/2` yields `3.5`, where every SQL database yields `3`. Masked in a bare projection (the reader's
`AsInt64` truncates back to 3) but visible wherever the value is compared or grouped:
`WHERE Total/Cnt = 3` misses the (7,2) row, `GROUP BY Total/Cnt` produces two groups for 3.5 and 3
(the group key hashes `m_type`). Fix: `(Integer, Integer)` always `FromInt(a/b)` — but switch the four
`AVG` sites to explicit real/decimal division first, or AVG silently starts truncating. Two existing
tests assert the current behaviour and must be updated.

### 4.10 EF Core provider — literals, translation, runtime

**Stock EF temporal mappings emit ANSI typed literals the grammar has no production for — major.** *(= KnownIssue #2, root cause found)*
[WitTypeMappingSource.cs:75-79](Sources/Providers/OutWit.Database.EntityFramework/Storage/WitTypeMappingSource.cs#L75) · [WitSqlParser.g4:527](Sources/Engine/OutWit.Database.Parser/Grammars/WitSqlParser.g4#L527)

Extracted verbatim from the referenced `Microsoft.EntityFrameworkCore.Relational` 9.0.6 assembly:
`"DATE '{0:yyyy-MM-dd}'"`, `"TIMESTAMP '{0:yyyy-MM-dd HH\:mm\:ss.fffffff}'"`,
`"TIMESTAMP '…zzz'"`, `"TIME '{0:HH\:mm\:ss}'"`. The `literal` rule has no `typeName STRING_LITERAL`
alternative; `DATE` is a `nonReservedKeyword` so it degrades to a `columnRef` then chokes on the
string, `TIMESTAMP` fails at the keyword. Affects `DateOnly` (the reported case), `DateTime`,
`DateTimeOffset` and `TimeOnly`, and — with no workaround — **every `HasData` seed row with a
temporal column**, because `WitMigrationsSqlGenerator` does not override `Generate(InsertDataOperation)`
and the base path literalises. `grep` for `HasData` across `Sources/` finds zero real hits, and no
test ever feeds provider-generated SQL to `WitSql.Parse`.

Fix: add typed literals to the grammar and produce *typed* `WitSqlValue`s. The cheaper
provider-side option (subclass the mappings, emit bare quoted strings) is **not safe alone**:
`WitSqlValue.CompareTo` falls back to ordinal string comparison for Text-vs-DateTime and
`AsString()` renders `DateTime` with `"o"` (a `T` separator), so a bare literal would parse and then
silently match nothing. Regression test: for each temporal type, feed
`FindMapping(t).GenerateSqlLiteral(v)` straight into `WitSql.Parse`.

**Text literals compared against temporal columns by ordinal string comparison — major.**
[WitSqlValue.Comparison.cs:47](Sources/Engine/OutWit.Database/Values/WitSqlValue.Comparison.cs#L47)
The write path coerces correctly (`WriteValue` stores ticks), the read path does not. `'T'` (0x54) >
`' '` (0x20) at index 10, so `WHERE CreatedAt > '2024-01-01 12:00:00'` returns a row stored at 09:00
on the same date — for *every* stored DateTime on that date, not just at midnight. Equality never
matches unless the literal is written in the exact 7-fraction-digit `"o"` form. `INTERVAL` orders
lexicographically (`"23:00:00"` judged ≥ `"1.00:00:00"`). `DateOnly`/`TimeOnly` work by format
coincidence. Currently unreachable via EF (typed literals fail at parse first) — but it is the
landmine directly under the obvious fix for KnownIssue #2, and it is live today for the documented
raw-SQL forms at [WitSQL.md:349](Docs/WitSQL.md#L349). On an indexed column the seek finds the right
row and the residual ordinal filter throws it away, so both plans are wrong. Fix: lift the Text
operand to the other side's type in `EvaluateBinary` before the comparison switch, using strict
`TryParse` (not the `As*` getters, which swallow failure and return `MinValue`); do **not** change
`CompareTo` alone or you break `GetHashCode`'s contract for hash join and group by.

**`Math.Max`/`Math.Min` translated to the aggregate `MAX`/`MIN` — critical.**
[WitMathMethodTranslator.cs:214-222](Sources/Providers/OutWit.Database.EntityFramework/Query/Translators/WitMathMethodTranslator.cs#L214)
WitSQL has no scalar two-argument MAX/MIN. In a SELECT list the planner reclassifies the whole query
as an aggregate and the streaming aggregate folds only `Arguments[0]`, so
`Select(i => Math.Max(i.Quota, i.Used))` over 3 rows returns **one** row containing `max(Quota)` —
no exception, and `WitDbDataReader.GetInt32` reads the value off the row ignoring the declared column
type, so materialisation succeeds. The common clamp idiom `Math.Max(x.Count, 0)` is broken the same
way. In WHERE or ORDER BY it instead throws `NotSupportedException: Function not supported: MAX`.
The tests assert `typeof(Math).GetMethod(...) != null`.
Fix: emit `CASE WHEN a >= b THEN a ELSE b END` via `sqlExpressionFactory.Case` (the generator already
overrides `VisitCase` and the evaluator handles searched CASE), or add scalar `GREATEST`/`LEAST` to
the evaluator under names `SqlFunctions.IsAggregate` does not claim. Interim: delete the two entries
— a translation failure beats one wrong row.

**`BulkInsert` omits the primary key of Guid-keyed entities — critical.**
[WitDbBulkExtensions.cs:463-469](Sources/Providers/OutWit.Database.EntityFramework/Extensions/WitDbBulkExtensions.cs#L463)
`GetInsertColumns` keeps a property only when `ValueGenerated == Never`. For an integer key that is
right (the DDL emits AUTOINCREMENT); for a Guid key nothing generates the value —
`IsAutoIncrement` is integer-only, so there is no default, and BulkInsert bypasses the change
tracker so EF's `SequentialGuidValueGenerator` never runs. Unspecified columns become
`WitSqlValue.Null`, and the NOT NULL check cannot catch it because **`PRIMARY KEY` does not imply
NOT NULL in this engine** and the migrations generator deliberately skips NOT NULL for PK columns.
PK validation skips all-NULL keys, and `UpdateIndexesOnInsert` skips null index keys. So N rows land
with `Id = NULL`; `AsGuid()` maps NULL → `Guid.Empty`, so EF materialises N rows sharing one key and
the identity map collapses them; `Find` never matches; the rows are unreachable. `SetOutputIdentity =
true` is the opposite failure — it force-writes `Id = 0` and reads nothing back, so row 2 collides.
`BulkInsertOrUpdate` is unaffected (it re-adds the PK unconditionally — the author saw this hazard
there and missed it here).
Fix: filter on *store*-generation (share the `IsAutoIncrement` predicate with the DDL generator);
throw for a client-generated key still at `default`; make `PRIMARY KEY` imply NOT NULL in the engine;
implement or delete `SetOutputIdentity`.

**`Close()` destroys the engine; `UseWitDbInMemory()` cannot persist — major.**
[WitDbConnection.cs:132-137](Sources/Providers/OutWit.Database.AdoNet/WitDbConnection.cs#L132) · [WitRelationalConnection.cs:45-61](Sources/Providers/OutWit.Database.EntityFramework/Storage/WitRelationalConnection.cs#L45)
`Close()` disposes the engine and nulls it; `Open()` rebuilds from the connection string; there is no
named/shared in-memory store. EF closes the connection when its open count hits zero, i.e. after
every operation, so `EnsureCreated(); Add; SaveChanges()` runs against three different empty
databases and throws "table not found". Every in-memory EF test is configuration-only (the file
header says so) and every executing test uses a file DB *plus* an explicit `OpenConnection()`, which
hides it. Note the provider README promises "database exists only for the lifetime of the context" —
the lifetime is actually the connection. Also: `EnsureDeleted()` returns true for in-memory while
doing nothing, so a "delete + recreate" between tests silently keeps the previous rows.
Minimal fix: `WitRelationalConnection` overrides `Close()` to no-op when in-memory and closes in
`Dispose()`. Proper fix: named shared-memory registry keyed by data source, which is also what the
multi-connection work needs.

**`BeginTransaction(isolationLevel)` silently downgrades to ReadCommitted — major.**
[WitDbConnection.cs:164-167](Sources/Providers/OutWit.Database.AdoNet/WitDbConnection.cs#L164)
Two independent bugs: `BEGIN TRANSACTION` is executed *before* `SET TRANSACTION ISOLATION LEVEL`
(the engine's own comment says the SET must come first), and `PendingIsolationLevel` lives on
`ContextExecution`, a fresh instance per `Execute` call — so a standalone SET writes to a throwaway
object and can never affect anything. `WitDbTransaction.IsolationLevel` faithfully reports what was
asked for, so the downgrade is invisible. The connection-string `Isolation Level=` default is also
discarded (`ExecuteBeginTransaction` always passes an explicit level). MVCC genuinely branches on the
level (read visibility, read-set tracking, commit validation), so this is not cosmetic — though
concurrent-transaction damage needs two transactions on one store, which the EF path cannot produce
today. Fix: move the pending level to engine session state; emit SET before BEGIN; call the
parameterless `BeginTransaction()` when no level was requested so the store default applies.

**`DbDataReader.HasRows` is true for an empty result set — major.**
[WitDbDataReader.cs:630](Sources/Providers/OutWit.Database.AdoNet/WitDbDataReader.cs#L630)
`WitSqlResult.HasRows` means "row-producing statement", not "non-empty" — even
`CreateEmptySelectResult` sets it true. So `if (!reader.HasRows) return NotFound();` takes the wrong
branch and the following getter throws `InvalidOperationException("No data available")`.
`RecordsAffected` is wrong in both directions too (0 for a SELECT instead of −1; −1 after `Close()`
for a DML because `Close()` nulls the result). Not EF-visible (EF uses `Read()` only). Fix:
one-row lookahead in the reader (`EnsurePeeked`), `HasRows => m_peekValid || m_hasRead`; snapshot
`RecordsAffected` in the constructor.

**`Mode=ReadOnly` / `Read Only=true` / `Mode=ReadWrite` are parsed, validated, then ignored — major.**
[WitDbConnection.cs:295-310](Sources/Providers/OutWit.Database.AdoNet/WitDbConnection.cs#L295)
`ConfigureStorage` branches only on `Memory`; `options.ReadOnly` is never read, and both keys are
excluded from the provider parameters. So `Mode=ReadOnly` opens read-write and a `DELETE` on that
connection mutates the database the caller explicitly protected; `Mode=ReadWrite` (documented "fail
if it doesn't exist") silently creates a new empty database on a typo'd path. `StorageFile` already
supports `readOnly` including a write guard, and the `"file"` provider factory already reads a
`readOnly` parameter — only the builder option and the wiring are missing. The two tests named
`ReadOnlyModeRequiresExistingFileTest`/`ReadWriteModeRequiresExistingFileTest` assert only
`State == Open`.

**`IsWitRowVersion()` yields a concurrency token nothing ever changes — major.**
[WitPropertyBuilderExtensions.cs:19-40](Sources/Providers/OutWit.Database.EntityFramework/Extensions/WitPropertyBuilderExtensions.cs#L19)
It produces `IsConcurrencyToken().ValueGeneratedOnAddOrUpdate().HasDefaultValue(1)` on an INT column.
`ValueGeneratedOnAddOrUpdate` means EF never writes it; the engine bumps only columns whose type is
`WitDataType.RowVersion`. So the token is the constant 1 forever and `WHERE "Version" = 1` always
matches — silent lost update, no `DbUpdateConcurrencyException`, and the README documents this as the
optimistic-concurrency feature. `ROWVERSION` is unreachable from EF at all (absent from
`m_storeTypeMappings` and from `GetColumnType`), so `[Timestamp] byte[]` maps to BLOB: non-nullable
gives `NOT NULL constraint failed` on the first insert, nullable gives `WHERE "RowVersion" IS NULL`
which always matches. Fix: add a `ROWVERSION` store type mapped to an 8-byte binary mapping, honour
`IsRowVersion`/`ColumnOperation.IsRowVersion`, and reimplement the helper on top of it (`byte[]`
only, no `HasDefaultValue`).

### 4.11 Packaging

**EF.Design shipped as a runtime dependency — major.**
[OutWit.Database.EntityFramework.csproj:15-17,22-24](Sources/Providers/OutWit.Database.EntityFramework/OutWit.Database.EntityFramework.csproj#L15)
`PrivateAssets=none` overrides EF.Design's `developmentDependency`, so the shipped nuspec records
`include="All"` and every consumer receives Roslyn, `Microsoft.Build*`, `Newtonsoft.Json`,
`Mono.TextTemplating` and both `BuildHost-net472/`/`BuildHost-netcore/` directories — proven from
`Samples/OutWit.Database.Samples.WebApiEF/bin/Debug/net9.0/`, whose csproj references only the
provider. Also pins consumers to MSBuild ≥ 17.14.28 and Roslyn 4.14.0 (NU1605 downgrade errors), and
forces `GenerateRuntimeConfigurationFiles` on class libraries. Npgsql and Sqlite have no EF.Design
dependency at all. Fix: `PrivateAssets=all` + `IncludeAssets=compile`. Design-typed code is confined
to `Design/*` + `AssemblyInfo.cs`, and `[DesignTimeProviderServices]` handles discovery.

**Antlr4BuildTasks shipped as a runtime dependency — major.**
[OutWit.Database.Parser.csproj:17](Sources/Engine/OutWit.Database.Parser/OutWit.Database.Parser.csproj#L17)
A build-time MSBuild task package that also ships a `lib/` asset, referenced with no `PrivateAssets`.
Because `OutWit.Database → Parser`, this contaminates **every** consumer of the SQL engine, EF or not:
`Samples/OutWit.Database.Samples.ConsoleApp/bin/Debug/net9.0/` (one ProjectReference) contains
`Antlr4BuildTasks.dll`, `Microsoft.Build.Framework.dll`, `Microsoft.Build.Utilities.Core.dll`,
`System.Configuration.ConfigurationManager.dll` and a `runtimes/win/…` EventLog asset — 2.8 MB of
Windows-specific build tooling in a platform-neutral database. Fix:
`PrivateAssets="all" ExcludeAssets="runtime;compile"` (build assets stay, so no consumer needs Java,
and the ANTLR task keeps working because the targets load it by absolute path).

**EF scaffolding is a verbatim SQLite copy — major.**
[WitDatabaseModelFactory.cs:93](Sources/Providers/OutWit.Database.EntityFramework/Design/Internal/WitDatabaseModelFactory.cs#L93)
Every metadata query is SQLite dialect: `SELECT name FROM sqlite_master …`, `PRAGMA table_info`,
`PRAGMA index_list`, `PRAGMA index_info`, `PRAGMA foreign_key_list`. Neither `sqlite_master` nor
`PRAGMA` exists anywhere in the engine or grammar (PRAGMA is roadmap-only). `[DesignTimeProviderServices]`
means `dotnet ef dbcontext scaffold` auto-discovers this and fails on the first statement with
`Table 'sqlite_master' not found`. The csproj `<Description>` advertises scaffolding. All the metadata
needed is available under `INFORMATION_SCHEMA` (Studio already queries it). Either reimplement against
that or throw `NotSupportedException` and remove the claim from the package description and tags.
Also: `Docs/WitSQL.md:1467-1481` documents `PRAGMA` as supported.

### 4.12 Test harness

**The migrations-differ branch that causes KnownIssue #1a is unreachable from any test — major.**
[WitMigrationsModelDifferTests.cs](Sources/Providers/OutWit.Database.EntityFramework.Tests/MigrationTests/WitMigrationsModelDifferTests.cs)
All 13 tests go through `GenerateCreateScript()`/`EnsureCreated()`, i.e. `GetDifferences(null, …)` —

**The entire EF query-translation layer has zero executing tests — major.**
[WitQuerySqlGeneratorTests.cs:71](Sources/Providers/OutWit.Database.EntityFramework.Tests/Query/WitQuerySqlGeneratorTests.cs#L71)

**A computed-column test file re-implements the generator — critical (test), and it hides a real defect.**
[WitMigrationsSqlGeneratorComputedColumnTests.cs:116-191](Sources/Providers/OutWit.Database.EntityFramework.Tests/MigrationTests/WitMigrationsSqlGeneratorComputedColumnTests.cs#L116)

## 5. Capability gaps for an honest "drop-in" claim

Ordered by shortest path. Items 1-4 gate everything else.

1. **Two or more open connections to one file must work.** Reference-counted `WitDatabase` registry
   keyed by canonical full path (plus a hash of storage-affecting options so two different configs
   for one path fail loudly); `FileShare.ReadWrite`; `FileLock` for cross-process. Do **not** share
   the `WitSqlEngine` — `m_currentTransaction` is engine-global, so sharing it would trade the
   `IOException` for silent cross-connection transaction bleed. Give each connection its own engine
   over the shared `WitDatabase`, and hoist `SchemaCatalog` into the shared instance (or add a schema
   version counter) or `CREATE TABLE` on connection 1 stays invisible to connection 2 — which is
   the same `Table 'X' not found` shape as KnownIssue #1b. Also: `ConnectionPool` is not a foundation
   to build on (it creates N independent engines and is never referenced by `WitDbConnection`;
   `Pooling=true` is parsed and ignored). **1 week.** Acceptance: un-`[Ignore]`
   [WitDbConnectionParallelAccessTests.cs:115,178,243,332](Sources/Providers/OutWit.Database.AdoNet.Tests/Parallel/WitDbConnectionParallelAccessTests.cs#L115).
2. **Deleting or copying a database must be all-or-nothing.** `EnsureDeleted` removes
   `<db>_indexes/`, the WAL, the journal and the lock file (expose one
   `WitDatabase.GetSidecarPaths(path)` so AdoNet, EF and Studio cannot drift); `DROP INDEX` deletes
   its file; index files carry a database identity + definition hash and are rebuilt on mismatch
   instead of trusting `Count > 0`; a copied `.witdb` with no `_indexes/` rebuilds rather than opening
   with silently empty indexes. **2 days.**
3. **`Skip` without `Take` must return rows.** **2 h** (see §3 item 3).
4. **Migrations must never silently do nothing.** Fix #1a; make the generator throw for any facet it
   cannot express (`RenameIndex`, `Add/DropPrimaryKey`, `AlterColumn` type changes, filtered/included
   index columns) instead of emitting comments or a wrong-shaped statement. With a fail-loud rule the
   whole class becomes visible. **1 day.**
5. **Enums and `char` must map without user intervention.** Delete the `IsEnum` short-circuit
   ([WitTypeMappingSource.cs:259](Sources/Providers/OutWit.Database.EntityFramework/Storage/WitTypeMappingSource.cs#L259))
   and the `typeof(char)` entry (`:150`) so EF's `ValueConverterSelector` attaches
   `EnumToNumberConverter`/`CharToStringConverter`. **Disagreement:** the ef-translation auditor filed
   this as critical ("enums are unusable"); the verifier refuted that — `RelationalTypeMapping.NormalizeEnumValue`
   converts a boxed int-backed enum to `int` in both `CreateParameter` and `GenerateSqlLiteral`, so
   plain `enum : int` round-trips fine today. What genuinely breaks is `char` (InvalidCastException on
   SaveChanges) and `enum : byte|short|long` (InvalidCastException in the value comparer; `enum : long`
   also gets an INT column). **2 h.**
6. **Concurrency tokens must work.** §3 item 33. Verify identity read-back end to end at the same
   time — **no test anywhere asserts `entity.Id != 0` after `SaveChanges`**, so store-generated key
   propagation is unverified even though the `RETURNING` shape looks right. **1 day.**
7. **Transaction semantics must match the contract.** SET before BEGIN; `override` the three
   savepoint methods and `SupportsSavepoints` (they are currently *hidden*, so a `DbTransaction`-typed
   caller gets `NotSupportedException`); implement or explicitly reject `EnlistTransaction`
   (`TransactionScope` currently fails). **1 day.**
8. **Facets.** `HasMaxLength`/`HasPrecision` are dropped from the store type, and nothing in the
   engine enforces `MaxLength`/`Precision` even when present, so a model that is length-checked on
   SQL Server accepts oversized values here. Clone mappings with facets **and** enforce them in
   `WitTypeConverter`. Column-level `COLLATE` does not exist in the grammar at all and
   `EvaluateCollate` explicitly ignores collation, so SQL Server's default case-insensitive
   comparison cannot be reproduced. **3 days** for facets; collation is a design decision.
9. **User-defined functions.** Design: `CREATE FUNCTION name(params) RETURNS type AS <expression>`
   restricted to a single scalar expression over the parameters (no statements, no recursion), stored
   in `SchemaCatalog` as serialized SQL exactly like a computed column, and resolved in
   `ExpressionEvaluator`'s function dispatch by substituting parameters into the parsed expression
   tree. This reuses machinery that already works and needs no new execution model. Grammar +
   catalog + evaluator + INFORMATION_SCHEMA.ROUTINES: **1 week.** Anything more (multi-statement
   bodies, table-valued functions, CLR-registered functions) is a separate project — and note EF Core
   only needs `HasDbFunction` mapping to a scalar, which the above covers. Prerequisite: fix the
   serializer's lossiness (§4.2) or persisted function bodies will corrupt the same way views do.
10. **Stored procedures.** Design: `CREATE PROCEDURE name(params) AS BEGIN <statement>; … END` plus a
    `CALL name(args)` statement, with the body stored as **original source text** (not re-serialized)
    and executed by a statement-list interpreter that already exists in embryonic form in
    `ExecuteTriggerBody`. That interpreter must first be fixed — it splits the body on `';'` with no
    string-literal awareness, so a semicolon inside a literal breaks the trigger at execution time.
    Realistic scope for parity with what EF's `InsertUsingStoredProcedure` needs (parameters, `OUT`
    parameters, a result set, rows-affected): **2-3 weeks**, and it needs
    `WitDbDataReader.NextResult` to work (it is hard-coded `false`, and multi-statement command text
    currently discards all but the last result). Until then, `WitModelValidator` should reject
    `InsertUsingStoredProcedure`/`Update…`/`Delete…` at model-validation time rather than letting
    `CALL "x"(…)` reach a parser that has no `CALL` production.
11. **Then:** APPLY/LATERAL, multi-table `ExecuteUpdate`/`ExecuteDelete`, JSON `ToJson()` owned
    entities, sequence facets (`IncrementBy` is dropped, so `UseHiLo()` hands out colliding keys and
    every `AlterSequence` emits `RESTART`), idempotent migration scripts (all `If(Not)Exists` guards
    return empty strings), statement batching (every `SaveChanges` row is its own round trip).
12. **Independently of code:** correct `Docs/WitSQL.md` — §22 UDFs, §23 stored procedures, §24
    column-level COLLATE, §26 CREATE/ATTACH DATABASE + VACUUM + PRAGMA, §28 multi-statement result
    blocks all document features with no production in the grammar. Publish a compatibility matrix
    listing schemas, stored procedures, temporal tables, spatial, arrays and ambient transactions as
    unsupported. A precise "supports X, not Y" is drop-in-honest; a spec that over-promises is not.

## 6. Testing plan

Ordered by value per hour. The pattern across this audit is that the suite is large and the
assertions are shaped so they cannot fail: `Assert.Pass()`, `Count > 0`, `Expression.ToString()`,
reflection over the BCL, `catch (ObjectDisposedException) { }`, and tests that re-implement the code
under test.

1. **Round-trip property test: everything the provider emits must parse.** For every mapping
   `WitTypeMappingSource.FindMapping` returns, call `GenerateSqlLiteral(sample)` and feed the result
   through `WitSql.ParseExpression`; for every `MigrationOperation` type, run
   `IMigrationsSqlGenerator.Generate` and feed each `MigrationCommand.CommandText` through
   `WitSql.Parse` (or expect a `NotSupportedException` for the deliberately unsupported ops). Run
   under `[SetCulture("de-DE")]` and `[SetCulture("fi-FI")]`. `grep` currently finds **zero** calls to
   `WitSql.Parse` in `Sources/Providers/`. This single harness catches KnownIssue #2, the negative
   `DEFAULT`, the culture bug, the comment-only migrations and the `GENERATED ALWAYS` mismatch. **1 day.**
2. **Grammar precedence table test.** For ~40 expression shapes, assert the *AST root type*, not the
   parse success: `X LIKE 'a%' AND Y = 1` → `Binary(And)`; `NOT Age > 30` → `Unary(Not)`;
   `X BETWEEN 1 AND 5 AND Y = 2` → `Binary(And)`; each with `NOT`, `OR`, `ESCAPE` and a second
   operator of the same family. Cheap, and it is the only thing standing between you and the next
   silent precedence bug. **4 h.**
3. **Executing EF translation harness.** One file-backed `DbContext`, a `[TestCaseSource]` of ~150
   LINQ expressions covering every arm of every registered translator, and three assertions per case:
   (a) snapshot the generated SQL via a `DbCommandInterceptor`; (b) compare the result set against the
   same lambda evaluated with LINQ-to-Objects over the seeded data; (c) assert no client-evaluation
   warning (`ConfigureWarnings(w => w.Throw(...))`). Include **both** constant shapes for every value
   type — inlined (`new DateOnly(...)`) and captured-local — because that difference *is* KnownIssue
   #2. Delete the reflection-only translator test files; they buy coverage credit for classes they
   never load. **2 days.** This catches `Math.Max`, `Skip`-only, integer division, GroupBy, joins.
4. **Fault-injecting `IStorage` + crash harness.** `StorageFaulty(inner, failAtWriteNo, FaultKind {
   Throw, SilentDrop, TornWrite, Truncate })` registered as extra factories in
   [StorageFactories.cs](Sources/Core/OutWit.Database.Core.Tests/Stores/StorageFactories.cs) so the
   whole existing store matrix re-runs under faults. Then a child-process crash harness: run a scripted
   op log, `Process.Kill()` at write N, reopen in the parent and assert (a) open succeeds or throws one
   documented exception type — never a hang, never `IndexOutOfRangeException`; (b) visible state equals
   the reference model at some commit boundary ≤ the kill point; (c) a full scan matches that state.
   Add `--blame-crash --blame-hang --blame-hang-timeout 120s` to CI. **3 days.** This is the only thing
   that would have caught the LSM fsync inversions, the unopenable-after-partial-sstable, the
   never-tested `RollbackJournal.Recover`, and the MVCC missing-fsync.
5. **Post-condition assertions on every "expected exception" test.** Every test that asserts a
   constraint violation must also assert that the table is byte-identical to its pre-statement
   snapshot, that `COUNT(*)` agrees with a scan, and that every row is findable through every index on
   it. `InsertWithUniqueIndexDuplicateThrowsTest` and `UpdateViolatesUniqueIndexThrowsTest` currently
   assert only `Throws<...>` and pass over a corrupted database. **4 h**, and it converts a whole class
   of existing tests from decorative to load-bearing.
6. **DDL-inside-transaction and rollback matrix.** For each of CREATE/DROP/RENAME TABLE, ADD/DROP
   COLUMN, CREATE/DROP INDEX, CREATE/DROP VIEW, TRUNCATE: run inside `BEGIN`…`COMMIT` and inside
   `BEGIN`…`ROLLBACK`, asserting the catalog, the persisted blob after reopening, and the row/column
   agreement. Run the whole matrix three times — default, `WithoutFileLocking()`, `WithMvcc()` —
   because the three configurations currently behave differently. **1 day.**
7. **Index/data invariant checker.** A test helper that, for a given table, asserts every row is
   reachable through every index and every index entry resolves to a row with that value. Call it at
   the end of every DML/DDL test. **4 h**, and it makes the index-divergence class permanently visible.
8. **Case and identifier matrix.** For each of INSERT/UPDATE/DELETE/TRUNCATE/CREATE INDEX, create the
   table as `Users` and issue the statement as `users`, asserting the same observable result as the
   all-`Users` variant, plus a reopen test for the rowid counter. **2 h.**
9. **Differential oracle at the SQL layer.** `Microsoft.EntityFrameworkCore.Sqlite` is already a test
   reference and unused. Run the same statement sequence against WitDatabase and SQLite and compare
   result sets. This is the highest-leverage way to find the *next* NULL-semantics, ordering or
   type-coercion divergence. **2 days** to bootstrap, then near-free per case.
10. **CI hygiene.** Per-project TRX file names (they currently all overwrite
    `test-results.trx`, so the uploaded artifact only ever contains the last project — visible in the
    red run on `1093db9`); an OS matrix (`FileShare.None`, `FileOptions.WriteThrough` and
    delete-while-open all behave differently on Windows vs Unix, and CI is ubuntu-only while `release.yml`
    matrixes Studio); `-p:ContinuousIntegrationBuild=true`; coverage collection (`coverlet.collector` is
    referenced by all seven test projects and never used); `dotnet list package --vulnerable
    --include-transitive` (which would have surfaced both packaging leaks); `Parser.Tests` targets
    net10.0 only, so the shipped net9.0 parser has no test run. **1 day.**
11. **Packaging assertion.** Unzip the produced nupkgs in `pack.yml` and fail if the nuspec mentions
    `Microsoft.EntityFrameworkCore.Design` or `Antlr4BuildTasks`, or if any `lib/**` entry is not a
    `.dll`/`.xml`. **1 h.**
12. **Parser fuzzing + nesting bound.** A depth/length budget before parsing (deeply nested parens
    overflow the stack, and `StackOverflowException` is process-fatal in .NET — Studio's query editor is
    a user-supplied-SQL surface), plus a corpus fuzz over the grammar. **1 day.**

### Claims that did not hold up

Recorded so they are not re-raised:

- **KnownIssue #1b is *not* a stale per-connection `SchemaCatalog` snapshot.** The proposed mechanism
  needs two live engines over one file, which `FileShare.None` makes impossible; the failing app would
  have thrown `IOException` first (independently confirmed by execution, §0.3). The catalog's
  load-once design is consistent with the storage contract. **Root cause since established — §0.1:
  the provider created the table as `Website`, not `Websites`.**

### Refuted or narrowed by execution (§0)

These were confirmed by an auditor and a verifier, then contradicted or narrowed when actually run.
Recorded so the fix effort goes where the evidence is.

- **`Math.Max`/`Math.Min` do not collapse to the aggregate.** `Select(x => Math.Max(x.Value, 3))`
  over 5 rows returned 5 scalar rows `[3,3,3,4,5]`. §4.10's `critical` rating is wrong for this shape;
  if a failing shape exists it has not been exhibited.
- **`BeginTransaction(IsolationLevel.Serializable)` reports `Serializable`.** The scorecard's
  "silently downgrades to ReadCommitted" is not observable through `DbTransaction.IsolationLevel`.
  Whether the level is *honoured* is untested — the claim needs restating as "not enforced", not
  "not accepted".
- **`DROP INDEX` + `CREATE INDEX` did not resurrect stale entries** in a single session (0 rows,
  correct). The `EnsureDeleted`-across-processes variant in §4.8 is untested and may still hold.
- **`ROLLBACK` did not leave the secondary index divergent** for a single-row insert (data and
  indexed lookup both 0). §4.8's mechanism may need a larger or multi-statement transaction.
- **DECIMAL index range scans did not drop rows** for two-decimal money values (`Amount > 9` over
  `5.00/9.50/10.00/100.00` → 3, correct). §3 item 22's lexicographic-ordering defect is real in the
  encoder, but a failing input has not been exhibited — find one before spending the format break.
- **60 insert+delete cycles of 40 KB overflow values did not exhaust the pinned page cache.** §3
  item 2's code defect is real; its "hard-fails on an ordinary DELETE" framing needs more pressure
  than that to demonstrate.
- **At-rest encryption is not "cryptographically void".** It fails closed on a wrong or missing
  password and does not leak plaintext to disk (§0.6). The defect is the key schedule and nonce
  discipline, which is still worth the rebuild in §3 item 21.
- **The unique-index defect went the other way**: a first pass using `COUNT(*)` appeared to clear it,
  and only a file reopen revealed the violating row had been persisted (§0.4). Any finding cleared by
  a `COUNT(*)` assertion in this report should be re-checked by selecting rows.
- **`EnsureCreated` does not crash with `InvalidCastException` for index-free models.** The
  read-optimized exception is raised by `ITable.CheckConstraints`, which is touched for every table
  *before* any index and before `GetDataOperations`, so the catch always fires first. Eight existing
  tests exercise exactly the shape claimed to be broken.
- **`enum` CLR properties are usable.** `RelationalTypeMapping.NormalizeEnumValue` converts a boxed
  int-backed enum to `int` in both `CreateParameter` and `GenerateSqlLiteral`, so insert, inlined
  literal, materialisation and change tracking all work. The genuine defects are `char` and
  non-`int`-backed enums (§5 item 5). The `Docs/KnownIssues.md:165` aside about enums is most likely
  about `WitDbBulkExtensions`, which reads values by raw reflection and bypasses type mappings
  entirely.
- **The MVCC stress tests are not as weak as reported.** `SnapshotIsolationConsistencyUnderLoadTest`
  asserts a real cross-key balance invariant under interleaving; `MvccRecordTests` has exact
  boundary tests for both visibility predicates; `TransactionWaitQueueTests` does assert FIFO/LIFO
  and priority ordering. Two genuine hygiene items survive: an empty `if (value == null) { }` in
  `ReadsDuringWriteTransactionTest` that enshrines an illegal SI read as acceptable, and a
  `null == null` hole in `GarbageCollectionDuringActiveTransactionsTest`.
